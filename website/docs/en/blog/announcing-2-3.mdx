## SWC Next parser \{#swc-next}

[SWC Next](https://github.com/swc-project/swc-next) is a fast JavaScript and TypeScript toolchain written in Rust. It is a rewrite of SWC from the ground up, built around a flat, ESTree-based AST for performance and extensibility. According to SWC Next's official benchmarks, its native parser is [2–4.5× as fast](https://github.com/swc-project/swc-next/blob/main/website/docs/docs/guide/benchmark.mdx#rust-parse) as SWC's; it is also tested against Test262, TypeScript, and Babel to ensure parser correctness.

Rspack 2.3 moves its JavaScript parser to SWC Next and, with its more compact AST and memory layout, also optimizes Rspack's parsing and traversal. Using 6 workers, parsing time and instruction counts changed as follows:

| Project   | Parsing time                  | Instructions                   |
| --------- | ----------------------------- | ------------------------------ |
| three.js  | 23.62 ms → 20.11 ms (**−14.9%**)  | 205.23 M → 155.07 M (**−24.4%**)   |
| React 10k | 207.16 ms → 193.86 ms (**−6.4%**) | 1597.67 M → 1421.29 M (**−11.0%**) |

## Performance

### Build performance

In this [benchmark project](https://github.com/LingyuCoder/rspack-react-10k-benchmark/actions/runs/40302457470), Rspack 2.3.0 reduces HMR and warm build times with caching by around 5% compared with 2.2.0.

### SplitChunks optimizations \{#split-chunks}

Rspack 2.3 improves chunk splitting in several ways to reduce duplicate code and output size:

- The new [`splitChunks.dedupDepth`](/plugins/split-chunks-plugin#splitchunksdedupdepth) option compares which chunks use each module to find more combinations of shared modules that can be extracted. It is enabled by default in production mode (`depth=1`).
- The improved chunk splitting algorithm reduces duplicate modules across chunks.
- Support for [`splitChunks.minRemainingSize`](/plugins/split-chunks-plugin#splitchunksminremainingsize) avoids leaving an overly small chunk after splitting, aligning the output with webpack's behavior.

The following table shows Brotli-compressed sizes before and after enabling `dedupDepth=1` in two large real-world projects:

| Project                   | Before   | After    | Saved   | Reduction |
| ------------------------- | -------- | -------- | ------- | --------- |
| Project A (client JS/CSS) | 23.22 MB | 22.67 MB | 550 KB  | **2.4%**  |
| Project B (client JS/CSS) | 39.97 MB | 36.00 MB | 3.97 MB | **9.9%**  |

### Memory improvements

Rspack 2.3 further reduces memory usage in large projects without sacrificing build performance. The following table compares RSS in a real-world project:

| -------- | ------------------- | --------: | --------: | --------- |
| Build    | Peak RSS            | 28.30 GiB | 20.53 GiB | **27.4%** |

If your project uses a large amount of memory, follow the [memory diagnostics guide](../guide/diagnostics/memory) to capture and submit snapshots. We can help analyze and optimize them.

## Experimental cache improvements \{#cache-improvements}

Rspack 2.3 introduces `newCache`, an experimental cache implementation that reuses build results at a finer granularity and reduces cache file size and write overhead.

The previous cache implementation had several limitations:

- Coarse cache granularity: it persisted the complete intermediate results of each compilation stage, such as the entire module graph during `make`. These results had to remain immutable, and the graph's complex state had caused errors or even panics when restoring the cache.
- Coupling with incremental compilation: incremental compilation targets development mode, while persistent caching also needs to support production builds. This made it difficult to reuse the same mechanism for some stages.
- Memory and persistent caches used different models, requiring special handling in multiple places.
- Serializing the persistent cache blocked compilation.

To address these issues, we introduced `newCache` with the following improvements:

- Finer cache granularity: it caches individual computation results, such as modules, without saving and restoring the entire module graph. This reduces correctness risks from complex graph state, and only the cached data needs to remain immutable.
- Decoupled from incremental compilation: caching works independently, making it easier to support both development and production builds.
- A unified cache model: memory and persistent caches use the same model, reducing special handling and making it easier to evict unused entries and control memory usage across development rebuilds.
- Deferred persistence: serialization and disk writes run during idle time or at the end of a build, reducing work that blocks compilation.

The feature is disabled by default. Enable it with [`experiments.newCache`](/config/experiments#experimentsnewcache):

```js title="rspack.config.mjs"
export default {
  cache: {
    type: 'persistent',
  },
  experiments: {
    newCache: true,
  },
};
```

The following tables compare the two cache implementations in [React 10k](https://github.com/rspack-contrib/build-tools-performance/tree/main/cases/react-10k) and a large real-world project.

React 10k:

| Metric                      | Old cache |  newCache |         Change |
| --------------------------- | --------: | --------: | -------------: |
| Total cold build time       |    2.11 s |    1.80 s |         -14.5% |
| Total warm build time       |  776.9 ms |  837.2 ms |          +7.8% |
| Peak memory for cold build  | 926.5 MiB | 781.3 MiB |         -15.7% |
| Peak memory for warm build  | 840.5 MiB | 840.7 MiB | About the same |
| Disk cache after warm build | 269.0 MiB |  57.2 MiB |         -78.7% |

Large real-world project:

| Metric                      |   Old cache |    newCache | Change |
| --------------------------- | ----------: | ----------: | -----: |
| Total cold build time       |     84.89 s |     83.47 s |  -1.7% |
| Total warm build time       |     33.18 s |     35.24 s |  +6.2% |
| Peak memory for cold build  |   11.55 GiB |    9.69 GiB | -16.1% |
| Peak memory for warm build  |    7.67 GiB |    8.23 GiB |  +7.3% |
| Disk cache after warm build | 3895.98 MiB | 1092.08 MiB | -72.0% |

In these tests, `newCache` reduces cache size by around 75% and lowers cache write overhead. Warm builds take longer in both tests, mainly due to a change in the caching strategy for the `make` phase: the previous implementation caches the entire module graph, while `newCache` caches individual modules and rebuilds their dependency relationships. Rebuilding the graph adds overhead, but using the current dependencies also makes it easier to ensure the graph is correct during rebuilds. In other phases where the cached content remains unchanged, `newCache` provides a noticeable performance improvement.

We will continue to optimize warm build performance and memory usage and plan to replace the previous implementation with `newCache` in a future minor release.

### Loader cache

The loader cache stores transformation results independently, without requiring caches for other build stages. Even when a module needs to be rebuilt, Rspack can reuse a loader's result and skip the transformation if its input, configuration, and relevant dependencies have not changed.

This is especially useful for expensive loaders such as babel-loader: a cache hit skips the transformation and reduces build time.

Enable the top-level `cache` and `experiments.newCache`, then set `cache: true` on a loader. You can configure other cache stages independently through [`experiments.newCache`](/config/experiments#cache-stages).

In a test using babel-loader to process around 10,000 simulated modules, enabling the loader cache substantially reduced build time:

| Parallel loaders | Cache disabled | Cache enabled | Speedup  |
| ---------------- | -------------- | ------------- | -------- |
| Disabled         | 63.75 s        | 11.16 s       | **5.7x** |
| Enabled          | 28.50 s        | 11.88 s       | **2.4x** |

You can also use [`cache.maxMemoryGenerations`](/config/cache#maxmemorygenerations) to control how many generations unused cache entries are kept in memory, balancing memory usage against disk reads.

## New features \{#features}

### Filter loaders by code content \{#loader-code-filter}

The new [`module.rules[].use.codeFilter`](/config/module-rules#rulesusecodefilter) option can skip unnecessary loader transformations based on the code content. For example, you can run a transformation only on files containing a `customMacro()` call:

```js title="rspack.config.mjs"
export default {
  module: {
    rules: [
      {
        test: /\.[cm]?[jt]sx?$/,
        use: [
          {
            loader: './custom-macro-loader.js',
            codeFilter: /\bcustomMacro\s*\(/,
          },
        ],
      },
    ],
  },
};
```

Rspack's core is written in Rust, so calling a JavaScript loader adds cross-language communication overhead, even when the code needs no transformation. `codeFilter` checks the code in Rust first and only calls the loader when a transformation is needed, reducing this overhead.

In a benchmark with 10,000 modules where only 10% needed transformation, `codeFilter` reduced loader calls by 90% and total build time from 622 ms to 481 ms, a reduction of about 23%.

### CSS bundling

This release improves support for CSS scenarios including CSS Modules scoping, composition, value references, and nested selectors. It also fixes issues with asynchronous style loading and relative `publicPath` values.

#### CSS-only entry points \{#css-entry}

A CSS-only entry can now emit just a stylesheet, which is useful for publishing themes or style libraries independently:

```js title="rspack.config.mjs"
export default {
  entry: {
    styles: './src/styles.css',
  },
  module: {
    rules: [{ test: /\.css$/i, type: 'css/auto' }],
  },
  output: {
    cssFilename: '[name].css',
  },
};
```

This configuration emits `styles.css` without generating an unnecessary `styles.js` file.

#### CSS externals

The new `css-import` and `asset-url` [external](/config/externals) types let you keep specified stylesheet or asset references in CSS external to the bundle.

```js title="rspack.config.js"
module.exports = {
  externals: {
    'normalize.css': 'css-import normalize.css',
    'https://cdn.example.com/theme.css':
      'css-import https://cdn.example.com/theme.css',
    'https://cdn.example.com/logo.png':
      'asset-url https://cdn.example.com/logo.png',
  },
};
```

Reference these external resources in CSS:

```css title="styles.css"
@import 'normalize.css';
@import url('https://cdn.example.com/theme.css');

.logo {
  background-image: url('https://cdn.example.com/logo.png');
}
```

The `@import` and `url()` references above are emitted unchanged and are not bundled.

CSS `@import`, `url()`, and `image-set()` also support `rspackIgnore` and `webpackIgnore` comments, letting you skip bundling specific assets:

```css title="styles.css"
@import /* rspackIgnore: true */ url('./runtime-theme.css');
```

### Resolution and lazy compilation

#### Resource path resolution \{#resource-resolution}

The new [`module.parser.javascript.dynamicUrl`](/config/module-parser#javascriptdynamicurl) option controls how dynamic `new URL()` paths are handled. When set to `false`, dynamic paths are evaluated at runtime while static URLs are still bundled. This is useful when dynamic assets are provided by a server or CDN.

In addition, `import.meta.glob` now resolves path aliases in patterns, and tsconfig resolution has improved support for relative paths and symlinks.

#### More reliable lazy compilation and async modules \{#lazy-compilation}

[Lazy compilation](/guide/advanced/lazy-compilation) improves initial module loading and subsequent rebuilds, avoiding repeated loads of already activated modules. It also fixes compatibility issues involving import attributes and path resolution.

Compatibility with nested asynchronous imports, deferred imports, and HMR has also improved.

### Watcher compatibility

[`experiments.nativeWatcher`](/config/experiments#experimentsnativewatcher) now provides more complete file timestamp information, improving compatibility with tools such as `ts-loader`, `webpack-virtual-modules`, and `vue-loader`.

The native watcher also supports functions for [`watchOptions.ignored`](/config/watch#watchoptionsignored) and better detects new directories and deleted or recreated files.

### Plugin and tool integration \{#plugin-integration}

This release adds or improves the following capabilities for plugin and loader authors:

- Read import attributes through `ResolveData.attributes` in [`NormalModuleFactory`](/api/plugin-api/normal-module-factory-hooks).
- Retrieve a chunk's filename template with `JavascriptModulesPlugin.getChunkFilenameTemplate()`.
- Read and write custom fields in `this._module.buildInfo` from parallel loaders.
- Improve webpack compatibility for plugin hooks and TypeScript types for loaders, externals, and stats.

### Other improvements

- **WebAssembly**: Added [`output.wasmStreamingFallback`](/config/output#outputwasmstreamingfallback) to allow disabling fallback to non-streaming loading.
- **Module output**: Improved support for CommonJS, ESM, and deferred imports.
- **Builds and caching**: Improved recovery after build failures and the caching experience on Windows.
- **HTTP imports**: [`experiments.buildHttp`](/config/experiments#experimentsbuildhttp) now performs stronger resource integrity checks in frozen builds.
- **Module Federation**: Fixed issues involving shared modules and manifests.
- **CLI**: Reduced default log output and improved startup; `create-rspack` now displays its current version.
- **React Compiler**: Fixed a crash when processing long expressions. HTML minification also preserves the execution boundaries between adjacent scripts.

See the [version comparison from 2.2.0 to 2.3.0](https://github.com/web-infra-dev/rspack/compare/v2.2.0...v2.3.0) and the [GitHub release notes](https://github.com/web-infra-dev/rspack/releases/tag/v2.3.0) for the full list of changes.

## Ecosystem

### Rsbuild

Rsbuild brings updates to output size, project creation, and the development experience.

#### Compact-hashed IDs by default \{#rsbuild-compact-hashed}

Rspack 2.2.0 introduced [`compact-hashed` IDs](/blog/announcing-2-2#compact-hashed-ids), which reduce output size by generating shorter, stable module and chunk IDs. Rsbuild now enables this strategy by default in production builds.

#### Better file size reporting \{#rsbuild-stats}

Modern browsers widely support compressed transfers, and servers or CDNs often compress text assets before sending them. Reporting compressed file sizes provides a closer estimate of what users download and helps assess the page loading experience.

Rsbuild's file size reports can show compressed sizes and use configurable gzip or Brotli compression levels, helping you estimate transfer sizes for your deployment.

[`performance.printFileSize.detail`](https://rsbuild.rs/config/performance/print-file-size#detail) also accepts a number to limit the report to the largest files in each environment. This helps you focus on the largest assets when a build produces many files. For example, show the 20 largest files and report Brotli sizes:

```ts title="rsbuild.config.ts"
export default {
  performance: {
    printFileSize: {
      detail: 20,
      compressed: { type: 'brotli', level: 5 },
    },
  },
};
```

#### Improved project templates \{#rsbuild-project-templates}

<span id="rsbuild-tanstack-start" />

[TanStack Start](https://tanstack.com/blog/start-adds-rsbuild-support) already supports building with Rsbuild. You can now also use `create-rsbuild` to create a TanStack Start project with React or Solid. For example, create a React project:

```bash
npx -y create-rsbuild@latest my-app -t tanstack-start-react
```

Use the `tanstack-start-solid` template for a Solid project.

<span id="rsbuild-lynx" />

`create-rsbuild` adds a [Lynx](https://lynxjs.org/) option. It delegates to `@lynx-js/create-lynx` to create a ReactLynx project with Rsbuild, helping you get started with cross-platform application development. For example, create a TypeScript project:

```bash
npx -y create-rsbuild@latest my-app -t lynx-ts
```

Use `lynx-js` to create a JavaScript project.

#### Better development experience \{#rsbuild-dev-experience}

When developing an application with both Web and server environments, [HMR updates can be applied](https://github.com/web-infra-dev/rsbuild/pull/8729) once the Web build succeeds, without waiting for the server build to finish. This makes frontend changes appear in the browser sooner.

You can also configure [`server.publicDir` per environment](https://github.com/web-infra-dev/rsbuild/pull/8711), giving client and server environments separate public asset directories or disabling them as needed.

#### Other improvements \{#rsbuild-other}

- **Web Workers**: `output.target: 'web-worker'` supports [`output.module: true`](https://rsbuild.rs/config/output/module#web-workers) for generating ES module output for module workers and compatible runtimes.
- **Host validation**: [`server.allowedHosts`](https://rsbuild.rs/config/server/allowed-hosts) can restrict hostnames accepted by the dev and preview servers. Validation is disabled by default and must be configured explicitly.
- **Preview server**: The new [`onClosePreviewServer`](https://rsbuild.rs/plugins/dev/hooks#onclosepreviewserver) hook lets plugins clean up resources when the preview server closes.
- **Plugin transforms**: Use `codeFilter` with [`api.transform`](https://github.com/web-infra-dev/rsbuild/pull/8722) to skip unnecessary transformations based on the code content.

See the [Rsbuild changelog](https://github.com/web-infra-dev/rsbuild/compare/v2.2.0...main) for the full list of changes.

### Rslib

#### Rslib 1.0 is now available \{#rslib-v1}

Rslib 1.0 has been released. See the [Rslib 1.0 release blog](https://rslib.rs/blog/v1-0) for details.

#### Inline Wasm modules \{#rslib-inline-wasm}

Rslib now supports inlining Wasm binaries into JavaScript output with `?inline`, so you do not need to distribute and load separate `.wasm` files:

```js
import { add } from './add.wasm?inline';

console.log(add(1, 2));
```

> See the [Wasm guide](https://rslib.rs/guide/advanced/wasm) for more examples.

Rslib 1.0.4 supports generating type declarations with TypeScript 7.1 Beta and using [Content Mappers](https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/#content-mappers) to extend type support for component files.

### Rsdoctor

[Rsdoctor 2.0](https://rsdoctor.rs/blog/release/release-note-2_0) is now available! The new release recommends using the Agent CLI for AI-assisted analysis. It can read build data directly and produce structured results.

It also improves Rspack analysis and supports reports for multiple compilers. Installation size is reduced by 56%, analysis time by 57%, and HMR time in development mode by around 47%.

### Rstest

#### Browser mode API improvements \{#rstest-browser-api}

Recent Browser Mode updates make it easier to test keyboard interactions and React hydration in a real browser:

- [`locator.pressSequentially()`](https://rstest.rs/api/runtime-api/browser-mode/locator#presssequentially) types text one character at a time, firing keyboard events for each character. This is useful for autocomplete inputs and other controls that respond to individual keystrokes.
- [`render()` in `@rstest/browser-react`](https://rstest.rs/guide/browser-testing/framework-guides) now accepts `hydrate` and `createRootOptions`. You can hydrate existing server-rendered markup in a supplied container and pass React root options through to test hydration behavior.

```ts
await page.getByLabel('Search').pressSequentially('rspack', { delay: 50 });
await expect.element(page.getByRole('listbox')).toBeVisible();
```

#### Screenshot testing \{#rstest-screenshot-testing}

[Rstest 0.12.4](https://github.com/web-infra-dev/rstest/releases/tag/v0.12.4) adds visual regression testing in Browser Mode with the Playwright provider. The new [`toMatchScreenshot()`](https://rstest.rs/api/runtime-api/browser-mode/assertion#toMatchScreenshot) matcher compares an element or page against a saved screenshot, helping catch visual changes that DOM assertions alone may miss.

```ts title="button.test.ts"
import { page } from '@rstest/browser';
import { expect, test } from '@rstest/core';

test('button appearance', async () => {
  document.body.innerHTML = '<button>Submit</button>';

  await expect(
    page.getByRole('button', { name: 'Submit' }),
  ).toMatchScreenshot();
  await expect(page).toMatchScreenshot('full-page', { fullPage: true });
});
```

When a comparison fails, Rstest saves the actual screenshot and a diff image for inspection. You can mask dynamic content, configure pixel difference tolerances, and update reference images with `--update`.

### Rspress

Rspress 2.1.0 supports [WebMCP](https://developer.chrome.com/docs/ai/webmcp) by default. Its built-in tools for querying site information, searching documentation, and navigating pages let browser-based Agents interact directly with documentation sites.

To try it, run the following code in a browser that supports WebMCP:

```js
const tools = await document.modelContext.getTools();
const tool = tools.find(({ name }) => name === 'rspress_get_current_page');
const page = JSON.parse(await document.modelContext.executeTool(tool, {}));
console.log(page.markdown);
```

You can also register custom tools with the `useWebMcp` Hook to extend how Agents interact with your site.

See the [WebMCP documentation](https://rspress.rs/guide/basic/webmcp) for details.

## Performance

### Performance improvements \{#performance-improvements}

Rspack 2.2 includes more than 30 performance optimizations, including:

- Improved the performance of core processes such as module concatenation, chunk splitting, and source map generation. In our benchmark, production build time dropped from 1822 ms to 1725 ms, an improvement of around 5%.
- Improved the performance of [CopyRspackPlugin](/plugins/rspack/copy-rspack-plugin). When copying a large number of files, it is now around 3-4x faster.
- Reduced the size of the Wasm build from 29.5 MB to 28.4 MB, a reduction of around 1.1 MB.
- Compiled SWC Wasm plugins in parallel, reducing plugin load time. For example, the load time of the [coverage-instrument](https://npmx.dev/package/swc-plugin-coverage-instrument) plugin was reduced by around 80%.
- Made built-in CSS parsing around 3x faster:

| Scenario              | Before   | After   | Improvement |
| --------------------- | -------- | ------- | ----------- |
| CSS development build | 320.3 ms | 87.2 ms | **3.7x**    |
| CSS production build  | 354.1 ms | 121 ms  | **2.9x**    |

### Better HMR \{#better-hmr}

Rspack 2.2 reduces unnecessary CSS requests during HMR. Previously, even when only JavaScript code changed, the browser would request the related CSS files during a hot update, compare their contents, and then determine whether the styles needed to be updated. The larger the stylesheet, the more time this extra step took.

With [#14682](https://github.com/web-infra-dev/rspack/pull/14682), Rspack now determines whether CSS has changed during the build and only requests CSS assets when needed, avoiding unnecessary HTTP requests. As a result, JavaScript hot update time no longer grows significantly with stylesheet size:

| Stylesheet size | Before  | After |
| --------------- | ------- | ----- |
| 0.5 MB          | ~50 ms  | ~5 ms |
| 2.1 MB          | ~170 ms | ~5 ms |
| 4.1 MB          | ~385 ms | ~6 ms |

In addition, [#14580](https://github.com/web-infra-dev/rspack/pull/14580) fixes an issue where styles briefly disappeared during hot updates with `mini-css-extract-plugin`, preventing page flicker.

### Shorter module IDs \{#compat-hashed-ids}

Rspack can now generate shorter IDs for modules and chunks. Compared with the existing `deterministic` strategy, the new `compat-hashed` strategy selects the shortest available prefix from a stable hash, further reducing output size while preserving ID stability and efficient runtime indexing.

In a real-world project, the output size changed as follows:

| **Metric**      | **`deterministic`** | **`compat-hashed`** | **Size reduction**  |
| --------------- | ------------------- | ------------------- | ------------------- |
| Minified JS     | 25,795.2 KB         | 25,710.6 KB         | **84.6 KB (0.33%)** |
| Minified + gzip | 7,103.3 KB          | 7,041.7 KB          | **61.6 KB (0.87%)** |

Enable this strategy through [`optimization.chunkIds`](/config/optimization#optimizationchunkids) and [`optimization.moduleIds`](/config/optimization#optimizationmoduleids):

```js title="rspack.config.mjs"
export default {
  optimization: {
    chunkIds: 'compat-hashed',
    moduleIds: 'compat-hashed',
  },
};
```

## New features

### `import.meta` improvements \{#import-meta-improvements}

Rspack now supports accessing Rspack-specific module variables through [`import.meta`](/api/runtime-api/module-variables#import-meta). Compared with CommonJS-style variables, this approach aligns better with ESM conventions and is preferred in ESM modules:

```js
// Before
__webpack_public_path__ = '/assets/';

// After
import.meta.rspackPublicPath = '/assets/';
```

In addition, [`import.meta.glob`](/api/runtime-api/module-variables#importmetaglob) adds a new `caseSensitive` option. When set to `false`, glob matching ignores letter casing in file paths:

```js
const modules = import.meta.glob('./pages/**/*.js', {
  caseSensitive: false,
});
```

### Browserslist Baseline support \{#browserslist-baseline}

Rspack now supports [Baseline queries in Browserslist](https://web.dev/articles/use-baseline-with-browserslist). You can specify target browser versions based on Baseline feature sets. For example, to target [**Baseline Widely available features**](https://web.dev/baseline), use:

```js title="rspack.config.mjs"
export default {
  target: 'browserslist:baseline widely available',
};
```

You can also query for a specific date with `baseline widely available on 2025-05-01`. See the [`target` configuration documentation](/config/target#baseline-queries) for details.

### Support for more platforms \{#more-linux-platforms}

Rspack now provides precompiled native bindings for more Linux platforms:

- RISC-V 64-bit: `linux-riscv64-gnu` and `linux-riscv64-musl`
- ppc64le and s390x architectures: `linux-ppc64-gnu` and `linux-s390x-gnu`

When installing Rspack on these platforms, you can use the corresponding native binding directly without falling back to the Wasm binding. See [Environment preparation](/guide/start/quick-start#environment-preparation) for the complete list of supported platforms.

## Ecosystem

### Rsbuild \{#rsbuild}

Rsbuild 2.2 has been released alongside Rspack 2.2.

#### Importing source text \{#import-text}

Rsbuild now supports using [import attributes](https://rsbuild.rs/guide/basic/static-assets#with-import-attributes) to import the raw contents of a file as a string:

```ts
import rawCSS from './example.css' with { type: 'text' };
```

> This aligns with the TC39 [Import Text proposal](https://github.com/tc39/proposal-import-text).

#### Optimized chunk splitting for Node.js \{#node-split-chunks}

Node.js builds now enable [chunk splitting](https://rsbuild.rs/config/split-chunks) by default, extracting shared modules into separate chunks to reduce duplicate code and SSR memory usage.

Here is [real-world data](https://github.com/TanStack/router/issues/8113#issuecomment-5366808113) provided by a TanStack Start user:

| Metric                                 | Rsbuild 2.1 | Rsbuild 2.2 | Change            |
| -------------------------------------- | ----------- | ----------- | ----------------- |
| Server output size                     | 298 MB      | 4.1 MB      | **98% reduction** |
| Memory usage after visiting all routes | 486 MB      | 129 MB      | **73% reduction** |
| Average route access time              | 7.2 ms      | 1.6 ms      | **78% reduction** |
| HMR time for shared components         | 7.1 s       | 0.98 s      | **86% reduction** |

> The test application contains 300 routes and 400 shared components. Actual improvements depend on the size and module structure of your project.

#### Solid v2 support \{#solid-v2}

Rsbuild now supports [Solid v2 RC](https://www.solidjs.com/blog/solid-2-0-rc-the-big-reveal) and uses Solid's new Rust compiler by default. In the official benchmark, the new compiler is **more than 20x faster** than the previous Babel implementation.

To try it, upgrade [@rsbuild/plugin-solid](https://rsbuild.rs/plugins/list/plugin-solid) to the v2 beta and remove the Babel plugin:

```diff
-import { pluginBabel } from '@rsbuild/plugin-babel';
import { pluginSolid } from '@rsbuild/plugin-solid';

export default {
  plugins: [
-   pluginBabel({
-     include: /\.(?:jsx|tsx)$/,
-   }),
    pluginSolid(),
  ],
};
```

#### Creating an Octane project \{#octane-template}

`create-rsbuild` now supports creating Octane projects. [Octane](https://octanejs.dev/) is a high-performance JavaScript UI framework that lets you write components with React APIs and compiles them directly to DOM code.

Run the following command to create an Octane project:

```bash
npx -y create-rsbuild@latest my-app -t octane-ts
```

#### Dynamic ports \{#dynamic-port}

Rsbuild now supports setting [`server.port`](https://rsbuild.rs/config/server/port#dynamic-port) to `0`, allowing the operating system to automatically assign an available port:

```ts title="rsbuild.config.ts"
export default {
  server: {
    port: 0,
  },
};
```

This is particularly useful in testing, as it avoids port conflicts when multiple tests start Rsbuild servers at the same time.

#### Custom minifier configurations \{#custom-minimizer-configs}

Rsbuild now supports configuring multiple minification options at once. Pass an array to [`minify.jsOptions`](https://rsbuild.rs/config/output/minify#minifyjsoptions) to apply different minification strategies to different outputs. For example, you can remove `console` calls only from the main bundle:

```ts title="rsbuild.config.ts"
export default {
  output: {
    minify: {
      jsOptions: [
        {
          include: /main\./,
          minimizerOptions: {
            compress: { drop_console: true },
          },
        },
        {
          exclude: /main\./,
          minimizerOptions: {
            compress: { drop_console: false },
          },
        },
      ],
    },
  },
};
```

#### Custom restart handling \{#restart-api}

Frameworks and tools built on Rsbuild can now control the restart process themselves.

The Rsbuild JavaScript API now supports a [`restart`](https://rsbuild.rs/api/javascript-api/core#restart-handling) option for handling restart requests from the development server (`rsbuild dev`) or watch builds (`rsbuild build --watch`):

```ts
import { createRsbuild } from '@rsbuild/core';

await createRsbuild({
  restart: (restart) => {
    // Custom restart logic
  },
});
```

Rsbuild plugins can also run custom logic by listening to the [`onRestart`](https://rsbuild.rs/plugins/dev/hooks#onrestart) hook.

### Rstest \{#rstest}

#### Module Federation testing \{#rstest-module-federation}

Rstest now supports Module Federation testing, allowing you to test real federated remote modules directly in Node, JSDOM, and Browser Mode environments.

Add `@module-federation/rstest` to your Rstest configuration:

```ts title="rstest.config.ts"
import { federation } from '@module-federation/rstest';
import { defineConfig } from '@rstest/core';

export default defineConfig({
  plugins: [
    federation({
      name: 'host',
      // options
    }),
  ],
});
```

> See the [Module Federation × Rstest integration documentation](https://module-federation.io/integrations/build-tool/rstest.html) for details.

#### Playwright E2E testing \{#rstest-playwright}

Rstest adds [`@rstest/playwright`](https://rstest.rs/guide/advanced/playwright), bringing Rstest's test runner, configuration, and reporting capabilities to E2E testing.

It provides Playwright-style assertion APIs for testing local development servers, preview servers, or deployed applications, while sharing a consistent workflow with unit tests:

```ts
import { expect, test } from '@rstest/playwright';

test('home page', async ({ page, serve }) => {
  const { url } = await serve('./dist/index.html');

  await page.goto(url);
  await expect(page.locator('h1')).toHaveText('Home');
});
```

#### Prebundled test environments \{#rstest-environment-prebundle}

Rstest now supports prebundling DOM test environments. When enabled, Rstest prebundles `jsdom` or `happy-dom` and reuses the output across workers, avoiding repeated parsing and initialization for every test file. This can significantly reduce overall test time in projects with many DOM tests.

In a [benchmark](https://github.com/web-infra-dev/rstest/releases/tag/v0.11.6), a project with 1,000 test cases saw the following improvements:

| Test environment    | Native loading | Prebundled | Time reduction |
| ------------------- | -------------- | ---------- | -------------- |
| `jsdom` 30.0.1      | 16.99 s        | 10.57 s    | **37.8%**      |
| `happy-dom` 20.11.1 | 6.35 s         | 2.98 s     | **53.0%**      |

This feature is disabled by default and can be enabled through [`testEnvironment.prebundle`](https://rstest.rs/config/test/test-environment#environment-prebundle):

```ts title="rstest.config.ts"
import { defineConfig } from '@rstest/core';

export default defineConfig({
  testEnvironment: {
    name: 'jsdom',
    prebundle: 'auto',
  },
});
```

When set to `'auto'`, Rstest only prebundles environment versions that have been verified as compatible. If it cannot build, load, or verify the prebundled output, it automatically falls back to native loading. Actual improvements vary depending on project size and runtime environment.

### Rslint \{#rslint}

#### More lint rules \{#typescript-eslint-support}

Rslint now includes more than 500 built-in lint rules and implements [all rules and presets](https://rslint.rs/api/presets/ts) from `@typescript-eslint`.

For example, you can enable all recommended type-aware rules through the `recommendedTypeChecked` preset:

```ts title="rslint.config.ts"
import { defineConfig, js, ts } from '@rslint/core';

export default defineConfig([
  js.configs.recommended,
  ts.configs.recommendedTypeChecked,
]);
```

#### Configuration type hints \{#config-type-hints}

`defineConfig` now provides complete type hints for ESLint core and `@typescript-eslint` rules, including rule names and option types.

```ts title="rslint.config.ts"
import { defineConfig } from '@rslint/core';

export default defineConfig([
  {
    rules: {
      '@typescript-eslint/no-floating-promises': 'error',
      '@typescript-eslint/no-unused-vars': [
        'error',
        { argsIgnorePattern: '^_' },
      ],
    },
  },
]);
```

#### Built-in common globals \{#built-in-globals}

`@rslint/core` now exports a [globals](https://rslint.rs/api/configuration/globals) object by default, containing global variable definitions for common environments such as browsers, Node.js, and Rstest:

```ts title="rslint.config.ts"
import { defineConfig, globals } from '@rslint/core';

export default defineConfig([
  {
    languageOptions: {
      globals: globals.browser,
    },
  },
]);
```

#### JavaScript API \{#rslint-js-api}

`@rslint/core` now provides a [JavaScript API](https://rslint.rs/guide/js-api) aligned with ESLint v10:

```ts
import { Rslint } from '@rslint/core';

const rslint = new Rslint({ fix: true });
const results = await rslint.lintFiles(['src/**/*.ts']);

await Rslint.outputFixes(results);
```

The JavaScript API also supports linting in-memory source code through `lintText` and providing configuration, `tsconfig.json`, and project files through `virtualFiles`. This is useful for integrations such as editors and Playgrounds that do not directly rely on the file system.

## Upgrade guide \{#upgrade-guide}

### Wasm plugins \{#wasm-plugin-breaking}

Rspack 2.2 upgrades `swc_core` from 76 to 77, changing the AST serialization format at the SWC Wasm plugin boundary. Wasm plugins built with an older version of SWC will no longer load, and builds will throw the following error:

```text
The version of the SWC Wasm plugin you're using might not be compatible with 'builtin:swc-loader'.
```

If you use an SWC Wasm plugin, rebuild it or upgrade to a version compatible with SWC 77. You can find plugin versions that match your current Rspack version at [plugins.swc.rs](https://plugins.swc.rs/).

> See [FAQ - SWC plugin version mismatch](/errors/swc-plugin-version) for details.

### RSC plugin \{#rsc-plugin-use-preinit}

Previously, the RSC plugin wrapped Client References and inserted CSS `<link>` tags when rendering components. Because the wrapped exports were no longer the original Client References, some export forms might not preserve the Client Reference marker.

Rspack 2.2 no longer wraps Client References. Instead, it loads CSS for client components through React's [`preinit`](https://react.dev/reference/react-dom/preinit).

This changes how CSS for client components is loaded in RSC and is a breaking change for RSC framework integrations. If you are integrating the Rspack RSC plugin, upgrade [`react-server-dom-rspack`](https://www.npmjs.com/package/react-server-dom-rspack) to `0.1.0` at the same time.

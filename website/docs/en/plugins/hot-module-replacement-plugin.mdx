# HotModuleReplacementPlugin

Enables hot module replacement (HMR).

## Examples

Enabling HMR is straightforward and in most cases no options are necessary.

Note that HMR can not be used in production build. You can use `process.env.NODE_ENV` to determine if it is a development environment.

```js title="rspack.config.mjs"
import { rspack } from '@rspack/core';
const isDev = process.env.NODE_ENV === 'development';

export default {
  plugins: [isDev && new rspack.HotModuleReplacementPlugin()],
};
```

## Runtime API

When you register the `HotModuleReplacementPlugin` plugin, Rspack will inject HMR related runtime APIs, such as `module.hot` and `import.meta.webpackHot`.

See [HMR API](/api/runtime-api/hmr) for more details.

With HMR enabled, ordinary JavaScript chunks carry their compilation hash. Before installing a chunk, Rspack compares this hash with the current runtime hash. A mismatched response cannot register module factories or run chunk runtime code. The import waits for any active update, applies available updates in order if needed, and retries the chunk request. If updates fail or no update leads to a compatible chunk, the import rejects. This does not require versioned chunk filenames.

Ordinary chunks and hot updates can download concurrently. A late response from an older compilation is rejected before it can overwrite updated factories. Each load attempt finishes before retrying, so waiting for a newer runtime does not block that runtime's update. A manual `check(false)` still only prepares the update; the caller decides when to call `apply()`.

The compilation hash is filled into ordinary JavaScript chunks after cached chunk rendering. It does not change their chunk hashes or disable incremental chunk hashing. The version metadata still changes their final contents, including chunks whose modules are unchanged, so those assets must be processed and emitted again.

Imports that are still loading during an automatic update also wait for that update to finish. Preparation waits for asynchronous status handlers and all hot-update files. If preparation or application fails, imports waiting for the update reject instead of remaining pending.

## Hot update manifest

During HMR, the runtime reads `hot-update.json` to determine which chunks to update and which chunks or modules to remove. The manifest lists their IDs; the JavaScript updates are stored in separate `*.hot-update.(js|mjs)` files.

This example updates the JavaScript and built-in CSS for the `main` chunk without removing any chunks or modules:

```json
{
  "c": ["main"],
  "r": [],
  "m": [],
  "css": { "c": ["main"] }
}
```

Each field below is an array of IDs:

| Field       | Meaning and purpose                                                                                 |
| ----------- | --------------------------------------------------------------------------------------------------- |
| `c`         | Chunks with JavaScript updates. The runtime loads their update files as needed.                     |
| `r`         | Chunks to remove from the current runtime.                                                          |
| `m`         | Modules to remove from the current runtime.                                                         |
| `css.c`     | Chunks with updated built-in CSS. The runtime reloads their stylesheets.                            |
| `css.r`     | Chunks whose built-in CSS was removed. The runtime removes their old stylesheets.                   |
| `miniCss.c` | Same as `css.c`, for CSS extracted by [CssExtractRspackPlugin](/plugins/css-extract-rspack-plugin). |
| `miniCss.r` | Same as `css.r`, for CSS extracted by `CssExtractRspackPlugin`.                                     |

`css` and `miniCss` are optional objects. Their `c` and `r` fields are omitted when empty.

When an entry gains chunk dependencies, the manifest can also contain `load.entries`. This object maps an entry chunk ID to the newly required chunk IDs. Only entries already loaded by the current runtime trigger supplemental downloads.

Supplemental JavaScript files use the hot-update filename with a `.full.js` suffix (`.full.mjs` for `.mjs` files) and contain the complete chunk factories. They are downloaded during `check` and installed during `apply`, before accept callbacks run. Unchanged factories preserve existing module instances. Once installed, the chunk participates in ordinary incremental updates, even if its original importer stops referencing it.

You can customize the manifest filename with [output.hotUpdateMainFilename](/config/output#outputhotupdatemainfilename). If you set `output.module` to `true`, Rspack generates the manifest as an ES module with the manifest data as its default export.

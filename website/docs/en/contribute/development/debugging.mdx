# Debugging

## Debugging with VS Code

1. Install `go install github.com/go-delve/delve/cmd/dlv@latest`
2. Install VS Code extension [rust-analyzer](https://marketplace.visualstudio.com/items?itemName=rust-lang.rust-analyzer) and [CodeLLDB](https://marketplace.visualstudio.com/items?itemName=vadimcn.vscode-lldb)
3. build `@rspack/cli` and napi binding by run `pnpm install && pnpm -w build:cli:dev`
4. In VS Code's `Run and Debug` tab, select `Debug Rspack` to start debugging the initial launch of `@rspack/cli` with a simple rspack project. This task can be configured in `.vscode/launch.json`.

## Using `@rspack-debug/core`

Frameworks and tools that integrate Rspack usually depend on the release build of `@rspack/core`. The release package is suitable for normal builds, but it does not include some debug-only capabilities. When you need these capabilities for local investigation, override `@rspack/core` with `@rspack-debug/core` in the project that runs the build.

For example, with pnpm:

```json title="package.json"
{
  "pnpm": {
    "overrides": {
      "@rspack/core": "npm:@rspack-debug/core@latest"
    },
    "peerDependencyRules": {
      "allowAny": ["@rspack/*"]
    }
  }
}
```

Then reinstall dependencies and run the original build command again. For example, if the project builds through Rsbuild:

```bash
pnpm install
RSPACK_PROFILE=OVERVIEW RSPACK_TRACE_LAYER=perfetto rsbuild build
```

`@rspack-debug/core` should only be used for local debugging and diagnostics. Prefer pinning it to the same version as the original `@rspack/core` dependency when investigating a version-specific issue, and remove the override after the investigation.

### Common debugging scenarios guide

#### Debugging Rust

Simply set breakpoints in the specified Rust code and start `Debug Rspack` to begin debugging.

#### Debugging JavaScript

When starting `Debug Rspack`, select the `--inspect` or `--inspect-brk` option, then start `Attach JavaScript` and choose the PID of the corresponding process.

#### Debugging a running Rspack process

When Rspack is integrated into other frameworks or tools (such as Nx), it may be difficult to independently start Rspack in Launch mode. In this case, you can debug the code through attach mode. Start `Attach Rust` and select the PID of the Rspack process, and start `Attach JavaScript` to debug JavaScript.

#### Debugging a Rspack process with a deadlock

When using `Attach Rust` to attach the debugger to the Rspack process, click the Pause button on the Debugger to set breakpoints at the deadlock scene.

## Allocative memory snapshots

Build the local binding and JavaScript packages with allocative instrumentation:

```bash
ALLOCATIVE=1 pnpm run build:binding:dev
pnpm run build:js
```

Run the workload with a fresh output directory and expose Node.js GC. Set `RSPACK_ALLOCATIVE_DIR` before creating the first compiler, when Rspack reads and caches whether JS capture is enabled.

```bash
RSPACK_ALLOCATIVE_DIR=/tmp/rspack-memory \
  node --expose-gc packages/rspack-cli/bin/rspack.js build
```

When `RSPACK_ALLOCATIVE_DIR` is set, Rspack installs an internal hook on `globalThis`. After cache finalization and after the build/rebuild future has released its mutable compiler borrow, the JS-thread completion callback runs `gc()`, synchronously writes the V8 snapshot, and traverses the live Rust `JsCompiler`. Its running guard and strong N-API reference remain held until capture finishes, before the JS completion callback. The `.heapsnapshot` file goes in `v8/` under the profile directory. The matching Rust `.allocative` and `.objects.json` files go in the profile directory itself. Standalone Rust workloads traverse core `Compiler` and produce Rust profiles only. One V8 environment per process can register for capture.

Use matching debug or profiling packages for paired Rust and JS snapshots. The ordinary release JS build removes the V8 snapshot code. To include it in a custom release build, set `ALLOCATIVE=1` when building both the binding and the JS package.

In an allocative build, native class instances have non-enumerable, read-only string properties `__rspackRustPtr` and `__rspackRustType`. The pointer identifies the Rust binding wrapper at its final N-API address. It is distinct from the address of a module or resolver referenced by that wrapper. Weak registration records live wrappers without keeping them alive or traversing their potentially active native targets. The owner traversal measures the wrapper and its fields, including its initialized `ManuallyDrop<Compiler>`; binding identity records add no byte weights. Opaque external handles are still reported as coverage limits.

Public JavaScript `Compiler`, `Compilation`, and `Cache` objects also expose an internal, non-enumerable reference to their own binding for profiling. The Rust traversal matches registered target addresses and types to the paths it actually visits. The combined profile places the measured Rust owner under its public JS Compiler: `JavaScript;Rspack;Compiler;rspack_binding_api::JsCompiler;compiler;…;rspack_core::compiler::Compiler`. The wrapper's other fields appear alongside `compiler`. Core Compiler is not traversed again as an independent root, and shared allocations are counted once across wrapper and core fields. Compiler-scoped targets are matched only for the compiler being captured, so other live compilers cannot be joined by type name. Retained Compilation objects follow their current native compilation slot after a rebuild.

By default, the V8 snapshot is redacted in memory before it is written. It keeps node types, IDs, references, and shallow sizes. V8 object names, string values, property names, and source locations are removed. Rspack matches pointers in memory and records the V8 node ID in the Rust identity file. To save a V8 snapshot with its original content, set `RSPACK_ALLOCATIVE_INCLUDE_CONTENT=1` when running the workload.

Convert a matching capture pair into folded stacks accepted by the existing allocative flamegraph renderer:

```bash
node scripts/v8-to-allocative.mjs /tmp/rspack-memory/v8/0-build.heapsnapshot
```

The script writes `.js.allocative`, `.combined.allocative`, and `.links.json` under `reports/` in the profile directory. Use `--out-dir` to select another existing directory. Reports use V8 node types and sizes by default, even when the input contains the original data. To include V8 object names and string values in the reports, pass `--include-content` with a snapshot captured with the original content.

Check `root_links` in `.links.json` for each public object's `binding_node_id` and `rust_target` path. `native_owners` records the owning JS-to-Rust edges; `measured: true` means the native wrapper itself was visited. `matched_bindings` counts wrapper matches; `matched_roots` counts public objects linked to visited Rust targets. A process-wide V8 snapshot can include objects outside the current compiler's Rust traversal; those roots remain unmatched. Capture again if an older snapshot lacks public binding edges or native target metadata. Linking changes attribution paths without adding bytes: the combined total equals the Rust total plus the V8 shallow-byte total.

The links report associates V8 node IDs with Rust wrapper types and paths. Its `category_bytes` field counts each V8 node's shallow `self_size` once across three categories.

- **V8 source and code** includes code nodes such as bytecode and compilation metadata, plus script source strings and their backing storage found before redaction.
- **Rspack** includes matched binding wrappers, marked JavaScript `Compiler`, `Compilation`, and `Cache` instances, and objects whose strong paths from the heap root all pass through these instances.
- **Shared or unknown** includes the remaining objects, including ones that are still reachable when those Rspack roots are excluded.

The JS flamegraph groups frames by category, and `.js.<category>.allocative` contains the folded stacks for one category. The combined flamegraph moves each native sample once under its measured JS owner. Other eligible JS frames use their matched target paths within that tree, falling back to wrapper identity paths when target metadata is unavailable. Compilation views and shared Cache links do not duplicate native subtrees. Weak edges are ignored for attribution. Paths are limited to 32 frames by default. Use `--max-depth` to change the limit. Capture a fresh snapshot for full category coverage if an older redacted snapshot lacks source and Rspack root tags.

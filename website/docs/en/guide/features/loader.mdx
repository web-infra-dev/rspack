# Loader

Rspack has built-in support for JavaScript, CSS, JSON, and static assets modules.

A loader is a transformer that converts various types of modules into Rspack supported types. By using different kinds of loaders, you can extend Rspack to process additional module types, including JSX, Markdown, Sass, Less, and more.

When Rspack bundles a module, it first pre-processes the module through loaders, transforming it into a Rspack supported module type, and then post-processes the module according to the [rules[].type](/config/module-rules#rulestype).

## Compatibility with webpack loaders

Rspack allows you to use most webpack loaders in the community. See [community loaders](/guide/start/ecosystem#loaders) to find loaders provided by the community.

If you find an unsupported loader, please feel free to communicate with us through [GitHub Issues](https://github.com/web-infra-dev/rspack/issues).

## Writing loaders

Refer to [Writing loaders](/api/loader-api/writing-loaders) to learn how to develop a loader.

## Example

### Using Less

You can use [less-loader](https://github.com/webpack/less-loader) to transform the contents of the `.less` file accordingly.

```js title="rspack.config.mjs"
export default {
  module: {
    rules: [
      {
        test: /\.less$/,
        use: [
          {
            loader: 'less-loader',
          },
        ],
        type: 'css',
      },
    ],
  },
};
```

[less-loader](https://github.com/webpack/less-loader) can transform Less files to Rspack-supported CSS module types, so you can set the type to `'css'` to instruct Rspack to use the CSS handling method that is natively supported for post-processing.

### Combining multiple loaders

You can chain multiple loaders for a particular [Rule](/config/module-rules#rule) match, with the loaders executed in right-to-left order.

For example, you can use [less-loader](https://github.com/webpack/less-loader) to do the transformation between Less to CSS types and [postcss-loader](https://github.com/webpack/postcss-loader) for the transformed source code to perform a secondary transformation, which will then get passed to Rspack's CSS post-processor for further processing.

```js title="rspack.config.mjs"
export default {
  module: {
    rules: [
      {
        test: /\.less$/,
        use: [
          {
            loader: 'postcss-loader',
          },
          {
            loader: 'less-loader',
          },
        ],
        type: 'css',
      },
    ],
  },
};
```

### Passing configuration items

You can use [rules[].use](/config/module-rules#rulesuse) to pass the relevant configuration to the loader, for example:

```js title="rspack.config.mjs"
export default {
  module: {
    rules: [
      {
        test: /\.css$/,
        use: [
          {
            loader: 'postcss-loader',
            options: {
              postcssOptions: {
                // ...
              },
            },
          },
        ],
        type: 'css',
      },
    ],
  },
};
```

### Using a custom loader

You can use a custom loader with Rspack. In the example below, we'll use the loader API to write a simple banner-loader.

The purpose of the banner-loader is to prepend a banner comment at the header of each module, such as a license notice:

```js
/**
 * MIT Licensed
 * Copyright (c) 2022-present ByteDance, Inc. and its affiliates.
 * https://github.com/web-infra-dev/rspack/blob/main/LICENSE
 */
```

Create a new `banner-loader.js` file under the root of the project with the following content:

```js title="banner-loader.js"
const BANNER = `/**
 * MIT Licensed
 * Copyright (c) 2022-present ByteDance, Inc. and its affiliates.
 * https://github.com/web-infra-dev/rspack/blob/main/LICENSE
 */`;

module.exports = function (content) {
  return `${BANNER}\n${content}`;
};
```

The first input to this loader is the content of the file, allowing us to process the file content and return the transformed result. The script file must be imported using CommonJS `require()`.

For example, to add a banner to all `*.js` files, the configuration might look like this:

```js title="rspack.config.mjs"
export default {
  module: {
    rules: [
      {
        test: /\.js$/,
        loader: './banner-loader.js',
      },
    ],
  },
};
```

For details, you can refer to [loader-api](/api/loader-api/)

## Parallel loader

Rspack supports running loaders in worker threads for parallel execution, which can better utilize multi-core CPUs and improve overall build performance.

To enable parallel execution for a loader, set the `parallel` option in [rules[].use](/config/module-rules#rulesuse):

```js title="rspack.config.mjs"
export default {
  module: {
    rules: [
      {
        test: /\.less$/,
        use: [
          {
            loader: 'less-loader',
            parallel: true,
            options: {},
          },
        ],
        type: 'css',
      },
    ],
  },
};
```

Setting `parallel: true` enables parallel execution with an automatically chosen number of worker threads.

When multiple loaders within the same rule have `parallel` enabled, Rspack executes them sequentially inside the same worker until it encounters a non-parallel loader or a Rust-implemented builtin loader. This preserves the loader execution order while maximizing parallel efficiency.

:::tip

- When parallel execution is enabled, `options` must be an object. Even if the loader has no options, you must explicitly set `options: {}`. Omitting `options` causes a configuration error.
- The loader options must comply with the [HTML structured clone algorithm](https://nodejs.org/api/worker_threads.html#portpostmessagevalue-transferlist), otherwise transmission will fail.
- In worker mode, most methods on `LoaderContext._compilation`, `LoaderContext._compiler`, and `LoaderContext._module` are not supported.

:::

For more details, see [rules[].use.parallel](/config/module-rules#rulesuseparallel).

## Loader cache

Rspack supports caching the transform results of individual loaders so unchanged inputs can skip repeated execution across builds or compilers, improving build performance for expensive loaders.

To enable loader caching, set [`cache: true`](/config/module-rules#rulesusecache) or pass an object `{ identifier, buildDependencies }` on a loader in `module.rules[].use`, along with the top-level [`cache`](/config/cache) and the `loader` stage of [`experiments.newCache`](/config/experiments#experimentsnewcache) (enabled by default when `experiments.newCache: true`):

```js title="rspack.config.mjs"
export default {
  cache: { type: 'persistent' },
  experiments: { newCache: true },
  module: {
    rules: [
      {
        test: /\.less$/,
        use: [{ loader: 'less-loader', cache: true }],
        type: 'css',
      },
    ],
  },
};
```

If the loader output depends on external settings (such as `mode`) or external configuration files (such as `babel.config.mjs`), configure `cache.identifier` and `cache.buildDependencies` so Rspack includes them in the loader cache etag:

```js title="rspack.config.mjs"
const mode = process.env.NODE_ENV || 'development';

export default {
  mode,
  cache: { type: 'persistent' },
  experiments: { newCache: true },
  module: {
    rules: [
      {
        test: /\.js$/,
        use: [
          {
            loader: 'babel-loader',
            cache: {
              identifier: JSON.stringify({ mode }),
              buildDependencies: ['./babel.config.mjs'],
            },
          },
        ],
      },
    ],
  },
};
```

With memory caching, compilers in the same process can share loader results. With persistent caching, compilers in the same process can share results and later builds can reuse them across processes when [`cache.storage.directory`](/config/cache#storagedirectory) and [`cache.version`](/config/cache#version) match.

:::tip

- Loader caching does not automatically track compiler settings such as `mode` or `target`, nor external configuration files read by the loader. Use [`cache.identifier`](/config/module-rules#rulesusecache) (for example, `JSON.stringify({ mode })`) to include external settings in the cache etag, and `cache.buildDependencies` to track external files or directories whose contents affect the output (with the same recursive directory and JS/TS transitive dependency resolution as top-level [`cache.buildDependencies`](/config/cache#builddependencies)).
- Ensure loader options can be losslessly serialized as JSON; otherwise, Rspack does not cache that loader's result (for example, when options contain functions, `Date`, or `RegExp` values).

:::

### When to use loader caching

A compiler's persistent cache already stores full module build results (including loader transforms and parsing) per compiler, and invalidates as a whole when [`cache.buildDependencies`](/config/cache#builddependencies) changes. Loader caching instead caches individual loader transforms independently, invalidating only when that loader's input, options, `cache.identifier`, tracked dependencies, or [`cache.version`](/config/cache#version) change.

Enable `cache: true` mainly for expensive loaders such as `babel-loader`, `less-loader`, or `sass-loader`. Normal warm rebuilds already hit the compiler's persistent cache, so lightweight loaders rarely benefit. For loaders with their own built-in cache (such as `babel-loader`'s `cacheDirectory`), disable that cache and use Rspack's loader caching instead for better performance and to avoid redundant caching.

Loader caching helps most when the compiler's persistent cache is invalidated or cannot be shared:

- **Configuration changes**: Rspack CLI adds the configuration file to `cache.buildDependencies`, so changing even an unrelated option such as `output.filename` invalidates the compiler's persistent cache and forces modules to rebuild. Because loader caching does not depend on `cache.buildDependencies`, Rspack can still reuse cached loader transforms.
- **Multi-compiler builds (such as SSR)**: Different compiler instances in an SSR setup have different configurations (such as `target`), so they cannot reuse each other's persistent cache even when using the same cache storage directory. Loader caching is not affected by this—once the client build finishes, the server build can reuse cached loader transforms for shared source files as long as the inputs, options, and dependencies match.

```js title="rspack.config.mjs"
const shared = {
  mode: 'development',
  cache: { type: 'persistent' },
  experiments: { newCache: true },
  module: {
    rules: [
      {
        test: /\.js$/,
        use: [
          {
            loader: 'babel-loader',
            options: { plugins: ['./your-custom-babel-plugin.cjs'] },
            cache: true,
          },
        ],
      },
    ],
  },
};

export default [
  {
    ...shared,
    name: 'client',
    target: 'web',
    entry: { client: './src/client.js' },
  },
  {
    ...shared,
    name: 'server',
    target: 'node',
    entry: { server: './src/server.js' },
    // Run after `client` so `server` can reuse cached loader results for shared files
    dependencies: ['client'],
  },
];
```

For loader authors, see [loader cache compatibility](/api/loader-api/writing-loaders#loader-cache-compatibility).

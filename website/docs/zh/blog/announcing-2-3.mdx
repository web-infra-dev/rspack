## SWC Next 集成 \{#swc-next}

[SWC Next](https://github.com/swc-project/swc-next) 是由 SWC 团队和 Rstack 团队共同开发的新一代 JavaScript 语言工具链，将成为 SWC 的下一个大版本。它采用受 [Yuku](https://github.com/yuku-toolchain/yuku) 启发的新解析器架构，以扁平的 ESTree AST 为核心，兼顾执行速度、内存效率和 JavaScript 扩展能力。

在基准测试中，SWC Next 的[原生解析速度](https://github.com/SoonIter/ecmascript-parser-benchmark-native)最高可达 SWC 的 **3 倍**，通过 [JavaScript API 解析](https://github.com/SoonIter/ecmascript-parser-benchmark-js)时最高可达 SWC 的 **10 倍**。我们也使用 Test262、TypeScript 和 Babel 等[多项测试集](https://next.swc.rs/guide/testing)验证解析器的正确性。

![](https://assets.rspack.rs/rspack/assets/rspack-v2-3-parser-performance.png)

目前，我们正在逐步将 SWC 的各个模块迁移到这一架构，并在 Rspack 中替换原有实现。Rspack 2.3 已将 JavaScript 解析器迁移至 SWC Next，并借助其更紧凑的 AST 和内存布局，优化了自身的解析和遍历流程。在基准测试中，解析阶段的耗时和指令数变化如下：

| 项目      | 解析阶段耗时                     | 指令数                            |
| --------- | -------------------------------- | --------------------------------- |
| three.js  | 23.6 ms → 20.1 ms（**−14.9%**）  | 205.2 M → 155.1 M（**−24.4%**）   |
| React 10k | 207.2 ms → 193.9 ms（**−6.4%**） | 1597.7 M → 1421.3 M（**−11.0%**） |

SWC Next 的下一目标是让开发者能够用 JavaScript 编写高性能的转换插件。目前，自定义代码转换通常依赖 Babel 插件或 SWC Wasm 插件，我们希望让开发者在享受 Rust 性能的同时，也能保留用 JavaScript 编写插件的灵活性。

SWC Next 的扁平 AST 支持 Rust 与 JavaScript 之间高效的数据交换，使这一设想成为可能。我们预计在 Rspack 2.4 或 2.5 中引入基于 SWC Next 的 loader，并支持 JavaScript 转换插件。

## 性能 \{#performance}

### 性能优化 \{#performance-improvements}

在多 agent 并行开发的场景下，多个构建进程和开发服务器可能同时运行，内存占用成为一个显著的瓶颈。因此，我们在 Rspack 2.3.0 中针对内存进行了优化，降低构建和开发过程中的内存占用。以下是一个真实项目的 RSS 对比：

| 场景  | 指标         | 2.2.0    | 2.3.0    | 降低      |
| ----- | ------------ | -------- | -------- | --------- |
| Build | 峰值 RSS     | 28.3 GiB | 20.5 GiB | **27.4%** |
| Build | 构建结束 RSS | 25.3 GiB | 16.1 GiB | **36.5%** |
| Dev   | 启动峰值 RSS | 28.6 GiB | 19.0 GiB | **33.8%** |
| Dev   | 稳态 RSS     | 28.9 GiB | 18.8 GiB | **34.8%** |

此外，Rspack 2.3 新增了基于 [allocative](https://github.com/facebook/buck2/tree/main/allocative) 的内存快照能力，帮助开发者定位构建过程中的内存热点。如果你的项目内存占用较高，可以按照[内存诊断指南](../guide/diagnostics/memory)采集并提交快照，我们会协助分析和优化。

得益于 SWC Next、内存优化和其他微优化，Rspack 2.3.0 的整体构建性能也得到提升。在基准测试中，构建性能相较 2.2.0 提升约 **5%**；在一些大型项目中，我们观察到了最高 **20%** 的性能提升。

### SplitChunks 优化 \{#split-chunks}

大型项目通常包含多个页面或入口，它们可能共同依赖大量模块。如果这些模块被重复打包到不同的输出文件中，就会增加产物体积，也可能让用户重复下载相同的代码。

针对这一问题，Rspack 2.3 引入了多项优化，减少重复模块，生成更精简的输出代码：

- 新增 [`splitChunks.dedupDepth`](/zh/plugins/split-chunks-plugin#splitchunksdedupdepth)，识别不同页面和入口之间更多可提取的共享模块组合，减少重复打包。该优化在生产模式下默认启用（`dedupDepth: 1`）。
- 支持 [`splitChunks.minRemainingSize`](/zh/plugins/split-chunks-plugin#splitchunksminremainingsize)，拆分代码时尽量避免留下过小的输出文件，有助于减少不必要的文件请求，同时让产物行为与 webpack 保持一致。
- 优化[代码拆分时的模块去重](/zh/guide/optimization/code-splitting#复用父级已经提供的模块)，更充分地复用已有模块，减少输出文件中的重复代码。

以下是两个大型真实项目在启用 `dedupDepth: 1` 前后的构建产物 Brotli 压缩体积对比：

| 项目                    | 优化前  | 优化后  | 节省   | 降幅     |
| ----------------------- | ------- | ------- | ------ | -------- |
| 项目 A（client JS/CSS） | 23.2 MB | 22.7 MB | 550 KB | **2.4%** |
| 项目 B（client JS/CSS） | 40.0 MB | 36.0 MB | 4.0 MB | **9.9%** |

## 实验性缓存改进 \{#cache-improvements}

Rspack 2.3 推出了实验性的新缓存。它可以更细粒度地复用构建结果，减少存储体积和写入开销。

旧缓存主要存在以下问题：

- 缓存粒度较粗：以编译阶段的完整中间结果为单位进行持久化，例如在 `make` 阶段保存和恢复整个模块图。整份中间结果需要保持不可变，复杂的图状态也曾导致缓存恢复时出错甚至 panic。
- 与增量构建耦合：增量构建面向开发模式，而持久化缓存还需要覆盖生产构建，部分阶段难以复用同一套机制。
- 内存缓存与持久化缓存的模型不统一，需要在多处增加特殊处理逻辑。
- 持久化缓存的序列化过程会阻塞编译。

为了解决这些问题，新缓存带来了以下改进：

- 细化缓存粒度：缓存模块等细粒度计算结果，无需保存和恢复整个模块图，降低复杂图状态带来的正确性风险。同时，只要求被缓存的内容保持不可变。
- 与增量构建解耦：让缓存独立于增量构建，便于覆盖开发和生产构建场景。
- 统一缓存模型：内存缓存和持久化缓存采用一致的模型，减少特殊处理逻辑，也更便于淘汰不再使用的缓存，控制多轮开发构建的内存占用。
- 推迟持久化操作：将序列化和磁盘写入安排在空闲或构建结束时执行，减少对编译的阻塞。

新缓存目前默认关闭，可以通过 [`experiments.newCache`](/zh/config/experiments#experimentsnewcache) 开启：

```js title="rspack.config.mjs"
export default {
  cache: {
    type: 'persistent',
  },
  experiments: {
    newCache: true,
  },
};
```

下面是在 [React 10k](https://github.com/rspack-contrib/build-tools-performance/tree/main/cases/react-10k) 和一个大型真实项目中，新旧缓存的对比结果。

React 10k：

| 指标               | 旧缓存    | 新缓存    | 变化     |
| ------------------ | --------- | --------- | -------- |
| 冷构建总耗时       | 2.1 s     | 1.8 s     | -14.5%   |
| 热构建总耗时       | 776.9 ms  | 837.2 ms  | +7.8%    |
| 冷构建峰值内存     | 926.5 MiB | 781.3 MiB | -15.7%   |
| 热构建峰值内存     | 840.5 MiB | 840.7 MiB | 基本持平 |
| 热构建后的存储占用 | 269.0 MiB | 57.2 MiB  | -78.7%   |

大型真实项目：

| 指标               | 旧缓存     | 新缓存     | 变化   |
| ------------------ | ---------- | ---------- | ------ |
| 冷构建总耗时       | 84.9 s     | 83.5 s     | -1.7%  |
| 热构建总耗时       | 33.2 s     | 35.2 s     | +6.2%  |
| 冷构建峰值内存     | 11.6 GiB   | 9.7 GiB    | -16.1% |
| 热构建峰值内存     | 7.7 GiB    | 8.2 GiB    | +7.3%  |
| 热构建后的存储占用 | 3896.0 MiB | 1092.1 MiB | -72.0% |

在上述测试中，新缓存将存储体积减少了约 75%，也降低了缓存写入开销。细粒度的模块缓存会使 `make` 阶段变慢，因为新缓存不再恢复整个模块图，而是重新构建模块之间的依赖关系。其他阶段则更快，抵消了部分额外开销，因此最终热构建总耗时仅小幅增加。这种取舍避免了恢复复杂的图状态，也更容易保证启用缓存时构建结果的正确性。

我们会优化热构建性能和内存占用，并计划在后续 minor 版本中用新缓存替换旧缓存。

### loader 缓存 \{#loader-cache}

Loader 缓存是新缓存的一部分，可以单独启用，无需启用其他构建阶段的缓存。

在一些场景中，例如交替使用 build 和 watch 模式时，模块缓存可能无法复用，但 loader 缓存仍可复用。例如，使用 babel-loader、less-loader 时，只要输出结果不受模式影响，且输入、配置和相关依赖保持一致，就可以在不同模式间复用缓存，加快构建速度。

启用顶层 `cache` 和 `experiments.newCache` 后，可以为 loader 设置 `cache: true`。其他缓存阶段可以通过 [`experiments.newCache`](/zh/config/experiments#cache-stages) 单独控制。

```js title="rspack.config.mjs"
export default {
  cache: {
    type: 'persistent',
  },
  experiments: {
    newCache: true,
  },
  module: {
    rules: [
      {
        test: /\.[cm]?[jt]sx?$/,
        use: [
          {
            loader: 'babel-loader',
            cache: true,
          },
        ],
      },
    ],
  },
};
```

在使用 babel-loader 处理约 10000 个模拟模块的测试中，开启 loader 缓存后，构建耗时降低：

| 并行 loader | 缓存关闭 | 缓存开启 | 加速比     |
| ----------- | -------- | -------- | ---------- |
| 关闭        | 63.8 s   | 11.2 s   | **5.7 倍** |
| 开启        | 28.5 s   | 11.9 s   | **2.4 倍** |

## 新特性 \{#features}

### 按代码内容过滤 loader \{#loader-code-filter}

新增的 [`module.rules[].use.codeFilter`](/zh/config/module-rules#rulesusecodefilter) 可以根据代码内容跳过不必要的 loader 转换。例如，只对包含 `customMacro()` 调用的文件执行转换：

```js title="rspack.config.mjs"
export default {
  module: {
    rules: [
      {
        test: /\.[cm]?[jt]sx?$/,
        use: [
          {
            loader: './custom-macro-loader.js',
            codeFilter: /\bcustomMacro\s*\(/,
          },
        ],
      },
    ],
  },
};
```

Rspack 核心由 Rust 编写，调用 JavaScript loader 时会产生跨语言通信开销，即使代码不需要转换，也要付出这部分成本。`codeFilter` 在 Rust 侧提前检查代码，只在需要转换时调用 loader，从而减少跨语言通信开销。

在包含 1 万个模块、仅 10% 的模块需要转换的测试中，`codeFilter` 避免了 90% 没有必要的 loader 调用，完整构建耗时从 622 ms 降至 481 ms，缩短约 23%。

### 内置 CSS \{#built-in-css}

本次更新改进了对更多 CSS 场景的支持，涵盖 CSS Modules 作用域、组合声明、值引用和嵌套选择器，同时修复了异步样式加载和相对 `publicPath` 相关的问题。

#### 独立构建样式入口 \{#css-entry}

独立发布主题或样式库时，通常只需要生成 CSS 文件。Rspack 现在支持将[纯 CSS 入口](/zh/guide/languages/css#css-entry)打包输出为独立的 CSS 文件，不会生成额外的 JavaScript 文件。例如：

```js title="rspack.config.mjs"
export default {
  entry: {
    styles: './src/styles.css',
  },
  module: {
    rules: [{ test: /\.css$/i, type: 'css/auto' }],
  },
  output: {
    cssFilename: '[name].css',
  },
};
```

该配置只会输出一个文件：`styles.css`。

#### 支持外部资源 \{#css-externals}

当 CSS 或图片由 CDN 等外部服务提供时，通常希望浏览器直接加载这些资源，而不是将它们打包进构建产物。

Rspack 新增 `css-import` 和 `asset-url` 两种 [external](/zh/config/externals) 类型，可以将 CSS 中的指定引用保留为[外部资源](/zh/guide/languages/css#external-resources)。例如，将样式表和图片配置为 external：

```js title="rspack.config.js"
module.exports = {
  externals: {
    'normalize.css': 'css-import normalize.css',
    'https://cdn.example.com/theme.css':
      'css-import https://cdn.example.com/theme.css',
    'https://cdn.example.com/logo.png':
      'asset-url https://cdn.example.com/logo.png',
  },
};
```

在 CSS 中引用这些外部资源：

```css title="styles.css"
@import 'normalize.css';
@import url('https://cdn.example.com/theme.css');

.logo {
  background-image: url('https://cdn.example.com/logo.png');
}
```

上述 `@import` 和 `url()` 会原样输出，不会参与打包。

CSS 中的 `@import`、`url()` 和 `image-set()` 也支持 [`rspackIgnore` 和 `webpackIgnore` 注释](/zh/guide/languages/css#magic-comments)，可以按需跳过资源打包：

```css title="styles.css"
@import /* rspackIgnore: true */ url('./runtime-theme.css');
```

### 依赖解析与按需编译 \{#resolution-and-lazy-compilation}

#### 更灵活的资源路径处理 \{#resource-resolution}

新增 [`module.parser.javascript.dynamicUrl`](/zh/config/module-parser#javascriptdynamicurl) 选项。设置为 `false` 时，动态 `new URL()` 路径会在运行时求值，静态 URL 仍会参与打包。这适用于由服务端或 CDN 提供动态资源的场景。

#### 更可靠的懒编译和异步模块 \{#lazy-compilation}

Rspack 2.3 改进了[懒编译](/zh/guide/advanced/lazy-compilation)，在模块首次加载和后续重建时避免重复加载已激活的模块，减少不必要的工作，并修复了导入属性和路径解析相关的兼容性问题。

嵌套异步导入、延迟导入和 HMR 的兼容性也得到了改善。

### Watcher 兼容性改进 \{#watcher-compatibility}

[`experiments.nativeWatcher`](/zh/config/experiments#experimentsnativewatcher) 现在提供了更完整的文件时间信息，改善了与 `ts-loader`、`webpack-virtual-modules`、`vue-loader` 等工具的兼容性。

原生 watcher 还支持使用函数配置 [`watchOptions.ignored`](/zh/config/watch#watchoptionsignored)，并改进了对新增目录、文件删除和重新创建的检测。

### 插件与工具集成 \{#plugin-integration}

本次更新为插件和 loader 作者新增或完善了以下能力：

- 通过 [`NormalModuleFactory`](/zh/api/plugin-api/normal-module-factory-hooks) 的 `ResolveData.attributes` 读取导入属性。
- 通过 `JavascriptModulesPlugin.getChunkFilenameTemplate()` 查询 chunk 的文件名模板。
- 并行 loader 支持读写 `this._module.buildInfo` 的自定义字段。
- 改善插件 hook 与 webpack 的兼容性，并完善 loader、externals 和 stats 的 TypeScript 类型。

### 其他改进 \{#other-improvements}

- **WebAssembly**：新增 [`output.wasmStreamingFallback`](/zh/config/output#outputwasmstreamingfallback)，支持关闭非流式加载回退。
- **HTTP 导入**：[`experiments.buildHttp`](/zh/config/experiments#experimentsbuildhttp) 加强了冻结构建中的资源完整性校验。

完整改动请查看 [2.2.0 至 2.3.0 的版本对比](https://github.com/web-infra-dev/rspack/compare/v2.2.0...v2.3.0)和 [GitHub Release Notes](https://github.com/web-infra-dev/rspack/releases/tag/v2.3.0)。

## 生态 \{#ecosystem}

随着 Rspack 2.3 发布，Rstack 生态中的 Rsbuild、Rslib、Rsdoctor、Rstest 和 Rspress 也带来了近期更新。

### Rsbuild \{#rsbuild}

#### TanStack CLI 支持 Rsbuild \{#rsbuild-tanstack-cli}

[TanStack CLI](https://tanstack.com/cli/latest/docs/cli-reference) 现已正式支持使用 Rsbuild 创建 TanStack Start 项目。创建项目时，添加 `--build-tool rsbuild` 即可选择 Rsbuild。例如，创建 React 项目：

```bash
npx @tanstack/cli@latest create my-app --framework React --build-tool rsbuild
```

`create-rsbuild` 也新增了 TanStack Start 选项，会自动调用 TanStack CLI 创建项目。你也可以通过以下命令直接选择该模板：

```bash
npx -y create-rsbuild@latest my-app -t tanstack-start-react
```

#### Lynx Rsbuild 插件 \{#rsbuild-lynx}

Lynx 推出了 [`@lynx-js/rsbuild-plugin`](https://lynxjs.org/next/zh/api/packages/rsbuild-plugin/index.html)，将原先封装在 Rspeedy 中的 Lynx 专属配置、默认值和构建适配整合到 `pluginLynx` 插件中。现在，Lynx 应用可以直接使用 Rsbuild 和该插件构建，无需依赖 Rspeedy 的封装。

你现在可以使用熟悉的 `rsbuild.config.ts` 和 Rsbuild CLI，按照 Rsbuild 文档配置项目，并继续使用现有的 Rsbuild 和 Lynx 构建插件。

`create-rsbuild` 也新增了 Lynx 选项，会自动调用 `@lynx-js/create-lynx` 创建项目。例如，创建使用 TypeScript 的 ReactLynx 项目：

```bash
npx -y create-rsbuild@latest my-app -t lynx-ts
```

#### 文件体积报告改进 \{#rsbuild-stats}

Rsbuild 的文件体积报告新增了 Brotli 压缩体积统计，并支持配置 gzip 和 Brotli 的压缩等级，便于按部署环境的压缩设置估算传输体积。统计 Brotli 压缩体积只需添加以下配置：

```ts title="rsbuild.config.ts"
export default {
  performance: {
    printFileSize: {
      compressed: { type: 'brotli' },
    },
  },
};
```

#### 其他改进 \{#rsbuild-other}

- **默认启用 compact-hashed ID**：生产构建默认使用 [`compact-hashed` ID](/zh/blog/announcing-2-2#compact-hashed-ids)，通过更短且稳定的模块和 chunk ID 减小产物体积。
- **开发体验**：开发同时包含客户端和服务端的应用时，前端代码变更可以[更快地在浏览器中生效](https://github.com/web-infra-dev/rsbuild/pull/8729)。
- **公共资源目录**：支持[按环境配置 `server.publicDir`](https://github.com/web-infra-dev/rsbuild/pull/8711)，为不同环境指定公共资源目录。
- **Web Worker**：当 `output.target` 为 `'web-worker'` 时，可以通过 [`output.module: true`](https://rsbuild.rs/zh/config/output/module#web-workers) 生成 ES 模块格式的产物。
- **Host 校验**：[`server.allowedHosts`](https://rsbuild.rs/zh/config/server/allowed-hosts) 可限制用于访问 dev server 和预览服务器的主机名。
- **预览服务器**：新增 [`onClosePreviewServer`](https://rsbuild.rs/zh/plugins/dev/hooks#onclosepreviewserver) hook，插件可在预览服务器关闭时清理资源。
- **插件转换**：[`api.transform`](https://github.com/web-infra-dev/rsbuild/pull/8722) 支持通过 `codeFilter` 根据代码内容跳过不必要的转换。

#### 支持 TypeScript 7.1 \{#typescript-7-1}

Rslib 1.0.4 支持使用 TypeScript 7.1 Beta 生成类型声明，并支持通过其新增的 [Content Mappers](https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/#content-mappers) 扩展类型生成能力。

使用时，只需安装对应的 mapper，并在 `tsconfig.json` 中注册它处理的文件扩展名。例如，假设已安装一个用于处理 CSS Modules 的 `example-css-modules-mapper`（示例包名），可以这样配置：

```json title="tsconfig.json"
{
  "contentMappers": [
    {
      "package": "example-css-modules-mapper",
      "extensions": [".module.css"]
    }
  ]
}
```

Rslib 在进行类型生成时会自动加载该 mapper，根据 CSS Modules 中的类名生成类型声明。

### Rstest \{#rstest}

#### 浏览器模式 API 增强 \{#rstest-browser-api}

浏览器模式近期新增了键盘交互和 React hydration 相关 API，方便在真实浏览器中测试这些行为：

- [`locator.pressSequentially()`](https://rstest.rs/zh/api/runtime-api/browser-mode/locator#presssequentially) 逐字符输入文本，并为每个字符触发键盘事件，适合测试自动补全输入框等需要响应单次按键的控件。
- [`@rstest/browser-react` 的 `render()`](https://rstest.rs/zh/guide/browser-testing/framework-guides) 新增 `hydrate` 和 `createRootOptions` 选项。你可以对指定容器中已有的服务端渲染内容执行 hydration，并传入 React root 选项来测试 hydration 行为。

```ts
await page.getByLabel('Search').pressSequentially('rspack', { delay: 50 });
await expect.element(page.getByRole('listbox')).toBeVisible();
```

#### 截图测试 \{#rstest-screenshot-testing}

[Rstest 0.12.4](https://github.com/web-infra-dev/rstest/releases/tag/v0.12.4) 在使用 Playwright provider 的浏览器模式中新增了视觉回归测试。通过 [`toMatchScreenshot()`](https://rstest.rs/zh/api/runtime-api/browser-mode/assertion#toMatchScreenshot)，你可以将元素或页面的截图与保存的基准图进行比较，发现仅靠 DOM 断言可能遗漏的视觉变化。

```ts title="button.test.ts"
import { page } from '@rstest/browser';
import { expect, test } from '@rstest/core';

test('button appearance', async () => {
  document.body.innerHTML = '<button>Submit</button>';

  await expect(
    page.getByRole('button', { name: 'Submit' }),
  ).toMatchScreenshot();
  await expect(page).toMatchScreenshot('full-page', { fullPage: true });
});
```

比较失败时，Rstest 会保存实际截图和差异图，方便排查问题。你还可以遮罩动态内容、配置像素差异容差，并通过 `--update` 更新基准图。

### Rspress \{#rspress}

Rspress 2.1.0 默认支持 [WebMCP](https://developer.chrome.com/docs/ai/webmcp)，内置站点信息查询、文档搜索和页面导航等工具，让浏览器中的 Agent 可以直接与文档站点交互。

想尝试该功能？在支持 WebMCP 的浏览器中，运行以下代码：

```js
const tools = await document.modelContext.getTools();
const tool = tools.find(({ name }) => name === 'rspress_get_current_page');
const page = JSON.parse(await document.modelContext.executeTool(tool, {}));
console.log(page.markdown);
```

你也可以通过 `useWebMcp` Hook 注册自定义工具，扩展站点与 Agent 的交互能力。

更多用法请参阅 [WebMCP 文档](https://rspress.rs/zh/guide/basic/webmcp)。

## 性能提升 \{#performance-improvements}

Rspack 2.2 包含 30 多项构建性能优化，例如：

- 优化模块合并、chunk 拆分和 Source Map 生成等核心流程性能。在基准测试中，生产构建时间从 1822 ms 降至 1725 ms，提升约 5.6%。
- 优化 [CopyRspackPlugin](/plugins/rspack/copy-rspack-plugin) 的性能。在复制大量文件时，性能提升约 3～4 倍。
- 优化 Wasm 产物的包体积，从 29.5 MB 降至 28.4 MB，减少约 1.1 MB。
- 并行编译 SWC Wasm 插件，这减少了插件加载时间。例如，[coverage-instrument](https://npmx.dev/package/swc-plugin-coverage-instrument) 插件的加载时间减少约 80%。
- 内置 CSS 的解析速度提升了约 3 倍：

| 场景         | 优化前   | 优化后  | 性能提升   |
| ------------ | -------- | ------- | ---------- |
| CSS 开发构建 | 320.3 ms | 87.2 ms | **3.7 倍** |
| CSS 生产构建 | 354.1 ms | 121 ms  | **2.9 倍** |

## HMR 改进 \{#better-hmr}

Rspack 2.2 让 HMR 的资源请求更加精确，热更新速度也更稳定。此前，即使只修改了 JavaScript 代码，HMR 也会在更新过程中加载相关的 CSS 文件，再在浏览器中对比内容是否变化，最后才决定要不要更新样式。

在 [#14682](https://github.com/web-infra-dev/rspack/pull/14682) 中，Rspack 改为在构建阶段判断 CSS chunk 是否发生变化，并据此精确控制 HMR 是否需要拉取 CSS 资源，省去了不必要的 HTTP 请求。在示例项目中，无论样式表体积多大，JavaScript 的热更新都能保持稳定的速度：

| 样式表体积          | 优化前  | 优化后 |
| ------------------- | ------- | ------ |
| 0.5 MB / 5k 条规则  | ~50 ms  | ~5 ms  |
| 2.1 MB / 20k 条规则 | ~170 ms | ~5 ms  |
| 4.1 MB / 40k 条规则 | ~385 ms | ~6 ms  |

此外，我们还[修复](https://github.com/web-infra-dev/rspack/pull/14580)了 `mini-css-extract-plugin` 在样式热更新过程中样式短暂丢失、导致页面闪烁的问题。

## `import.meta` 改进 \{#import-meta-improvements}

Rspack 2.2 新增了一组基于 [`import.meta`](/api/runtime-api/module-variables#import-meta) 的运行时 API。相比 CommonJS 风格的全局变量，它们更符合 ESM 标准，推荐在 ESM 模块中优先使用：

```js
// Before
__webpack_public_path__ = '/assets/';

// After
import.meta.rspackPublicPath = '/assets/';
```

此外，[`import.meta.glob`](/api/runtime-api/module-variables#importmetaglob) 新增了 `caseSensitive` 选项。设置为 `false` 时，glob 匹配会忽略文件路径的大小写：

```js
const modules = import.meta.glob('./pages/**/*.js', {
  caseSensitive: false,
});
```

## 简短的模块 ID \{#compat-hashed-ids}

Rspack 现在支持为模块和 chunk 生成更短的 ID。相比 `deterministic`，新的 `compat-hashed` 策略会从稳定 hash 中选取最短可用前缀，在保持 ID 稳定和运行时索引效率的同时，进一步减小产物体积。

在一个真实项目中，产物体积变化如下：

| **指标**        | **`deterministic`** | **`compat-hashed`** | **体积减少**         |
| --------------- | ------------------- | ------------------- | -------------------- |
| Minified JS     | 25,795.2 KB         | 25,710.6 KB         | **84.6 KB（0.33%）** |
| Minified + gzip | 7,103.3 KB          | 7,041.7 KB          | **61.6 KB（0.87%）** |

可以通过 [`optimization.chunkIds`](/config/optimization#optimizationchunkids) 和 [`optimization.moduleIds`](/config/optimization#optimizationmoduleids) 选项开启：

```js title="rspack.config.mjs"
export default {
  optimization: {
    chunkIds: 'compat-hashed',
    moduleIds: 'compat-hashed',
  },
};
```

## 生态

### Rsbuild \{#rsbuild}

Rsbuild 2.2 已经与 Rspack 2.2 同步发布。

#### 导入源文本 \{#import-text}

Rsbuild 现在支持使用 [import attributes 语法](https://rsbuild.rs/zh/guide/basic/static-assets#with-import-attributes) 将文件原始内容作为字符串导入：

```ts
import rawCSS from './example.css' with { type: 'text' };
```

> 这与 TC39 的 [Import Text 提案](https://github.com/tc39/proposal-import-text) 保持一致。

#### Node.js 拆包优化 \{#node-split-chunks}

Node.js 构建现在会默认启用 [chunk 拆分](https://rsbuild.rs/zh/config/split-chunks)，将共享模块提取为独立的 chunk，从而减少重复代码和 SSR 内存占用。

下面是 TanStack Start 用户提供的 [实测数据](https://github.com/TanStack/router/issues/8113#issuecomment-5366808113)：

| 指标                     | Rsbuild 2.1 | Rsbuild 2.2 | 变化         |
| ------------------------ | ----------- | ----------- | ------------ |
| 服务端产物体积           | 298 MB      | 4.1 MB      | **减少 98%** |
| 访问所有路由后的内存占用 | 486 MB      | 129 MB      | **减少 73%** |
| 路由平均访问耗时         | 7.2 ms      | 1.6 ms      | **减少 78%** |
| 共享组件的 HMR 耗时      | 7.1 s       | 0.98 s      | **减少 86%** |

> 测试应用包含 300 个路由和 400 个共享组件，实际收益取决于项目规模和模块结构。

#### 支持 Solid v2 \{#solid-v2}

Rsbuild 现在支持 [Solid v2 RC](https://www.solidjs.com/blog/solid-2-0-rc-the-big-reveal)，并默认使用 Solid 全新的 Rust 编译器。在官方的基准测试中，新编译器的编译速度相比此前的 Babel 实现提升 **20 倍以上**。

升级 [@rsbuild/plugin-solid](https://rsbuild.rs/zh/plugins/list/plugin-solid) 至 v2 beta 版本，然后移除 Babel 插件即可体验：

```diff
-import { pluginBabel } from '@rsbuild/plugin-babel';
import { pluginSolid } from '@rsbuild/plugin-solid';

export default {
  plugins: [
-   pluginBabel({
-     include: /\.(?:jsx|tsx)$/,
-   }),
    pluginSolid(),
  ],
};
```

#### 创建 Octane 项目 \{#octane-template}

`create-rsbuild` 现在支持创建 Octane 项目。[Octane](https://octanejs.dev/) 是一个高性能 JavaScript UI 框架，允许你通过 React API 编写组件，并将其编译为直接的 DOM 代码。

运行以下命令即可创建一个 Octane 项目：

```bash
npx -y create-rsbuild@latest my-app -t octane-ts
```

#### 动态端口 \{#dynamic-port}

Rsbuild 现在支持将 [`server.port`](https://rsbuild.rs/zh/config/server/port#动态端口) 设置为 `0`，由操作系统自动分配一个可用端口：

```ts title="rsbuild.config.ts"
export default {
  server: {
    port: 0,
  },
};
```

这在测试场景中尤其有用，可以避免多个测试同时启动 Rsbuild server 时发生端口冲突。

#### 定制压缩配置 \{#custom-minimizer-configs}

Rsbuild 现在支持同时配置多种压缩选项。为 [`minify.jsOptions`](https://rsbuild.rs/zh/config/output/minify#minifyjsoptions) 传入数组，可以针对不同产物设置不同的压缩策略。例如，仅移除主 bundle 中的 `console` 调用：

```ts title="rsbuild.config.ts"
export default {
  output: {
    minify: {
      jsOptions: [
        {
          include: /main\./,
          minimizerOptions: {
            compress: { drop_console: true },
          },
        },
        {
          exclude: /main\./,
          minimizerOptions: {
            compress: { drop_console: false },
          },
        },
      ],
    },
  },
};
```

#### 自定义重启流程 \{#restart-api}

基于 Rsbuild 的框架和工具现在可以自行控制重启流程。

Rsbuild 的 JavaScript API 现已支持 [`restart`](https://rsbuild.rs/zh/api/javascript-api/core#restart-handling) 选项，用于处理开发服务器（`rsbuild dev`）或监听构建（`rsbuild build --watch`）的重启请求：

```ts
import { createRsbuild } from '@rsbuild/core';

await createRsbuild({
  restart: (restart) => {
    // 自定义重启逻辑
  },
});
```

Rsbuild 插件也可以通过监听 [`onRestart`](https://rsbuild.rs/zh/plugins/dev/hooks#onrestart) hook 来执行自定义逻辑。

### Rstest \{#rstest}

#### Playwright E2E 测试 \{#rstest-playwright}

Rstest 新增了 [`@rstest/playwright`](https://rstest.rs/zh/guide/advanced/playwright)，让 E2E 测试也能使用 Rstest 的测试运行器、配置和报告能力。

它提供 Playwright 风格的断言 API，可用于测试本地开发服务器、预览服务器或已部署的应用，并与单元测试共享一致的工作流：

```ts
import { expect, test } from '@rstest/playwright';

test('home page', async ({ page, serve }) => {
  const { url } = await serve('./dist/index.html');

  await page.goto(url);
  await expect(page.locator('h1')).toHaveText('Home');
});
```

#### 模块联邦测试 \{#rstest-module-federation}

Rstest 现在支持模块联邦测试：可以在 Node、JSDOM 和 Browser Mode 环境下，直接测试真实的联邦远程模块。

在 Rstest 配置文件中引入 `@module-federation/rstest` 即可：

```ts title="rstest.config.ts"
import { federation } from '@module-federation/rstest';
import { defineConfig } from '@rstest/core';

export default defineConfig({
  plugins: [
    federation({
      name: 'host',
      // options
    }),
  ],
});
```

> 详见 [Module Federation × Rstest 集成文档](https://module-federation.io/integrations/build-tool/rstest.html)。

#### 预打包测试环境 \{#rstest-environment-prebundle}

Rstest 现在支持预打包 DOM 测试环境。开启后，Rstest 会预打包 `jsdom` 或 `happy-dom`，并在多个 worker 之间复用产物，避免为每个测试文件重复解析和初始化环境。对于 DOM 测试较多的项目，这可以显著缩短整体测试耗时。

在 [基准测试](https://github.com/web-infra-dev/rstest/releases/tag/v0.11.6) 中，一个包含 1000 个测试用例的项目取得了以下收益：

| 测试环境            | 原生加载 | 预打包  | 耗时降低  |
| ------------------- | -------- | ------- | --------- |
| `jsdom` 30.0.1      | 16.99 s  | 10.57 s | **37.8%** |
| `happy-dom` 20.11.1 | 6.35 s   | 2.98 s  | **53.0%** |

该能力默认关闭，可通过 [`testEnvironment.prebundle`](https://rstest.rs/zh/config/test/test-environment#环境预打包) 开启：

```ts title="rstest.config.ts"
import { defineConfig } from '@rstest/core';

export default defineConfig({
  testEnvironment: {
    name: 'jsdom',
    prebundle: 'auto',
  },
});
```

设置为 `'auto'` 时，Rstest 只会预打包已验证兼容的环境版本；如果无法构建、加载或验证预打包产物，则会自动回退到原生加载。实际收益会因项目规模和运行环境而异。

### Rslint \{#rslint}

#### 完整的 typescript-eslint 支持 \{#typescript-eslint-support}

Rslint 0.8.1 已内置实现全部 `@typescript-eslint` 规则，并完整对齐 typescript-eslint 的官方预设体系，支持 `recommended`、`recommendedTypeChecked`、`strict`、`strictTypeChecked`、`stylistic` 和 `stylisticTypeChecked`。

通过 `defineConfig` 配置 ESLint core 和 `@typescript-eslint` 规则时，编辑器可以自动补全规则名称、严重级别和规则选项，并在 Rslint 运行前发现无效配置。此外，`@rslint/core` 还内置了 Browser、Node.js、Worker 和 Rstest 等运行环境的 `globals`：

```ts title="rslint.config.ts"
import { defineConfig, globals, js, ts } from '@rslint/core';

export default defineConfig([
  js.configs.recommended,
  ts.configs.recommendedTypeChecked,
  {
    files: ['src/client/**'],
    languageOptions: {
      globals: globals.browser,
    },
    rules: {
      '@typescript-eslint/no-floating-promises': 'error',
      '@typescript-eslint/no-unused-vars': [
        'error',
        { argsIgnorePattern: '^_' },
      ],
    },
  },
]);
```

#### JavaScript API \{#rslint-js-api}

`@rslint/core` 现在提供了与 ESLint v10 形态对齐的 [JavaScript API](https://rslint.rs/guide/js-api)：

```ts
import { Rslint } from '@rslint/core';

const rslint = new Rslint({ fix: true });
const results = await rslint.lintFiles(['src/**/*.ts']);
await Rslint.outputFixes(results);
```

JavaScript API 也支持通过 `lintText` 检查内存中的源码，并使用 `virtualFiles` 提供配置、`tsconfig.json` 和项目文件，适合用于编辑器和 Playground 等不直接依赖磁盘文件的集成场景。

## 升级指南 \{#upgrade-guide}

### Wasm 插件 \{#wasm-plugin-breaking}

Rspack 2.2 将 `swc_core` 从 76 升级至 77，这改变了 SWC Wasm 插件边界上的 AST 序列化格式。基于旧版 SWC 构建的 Wasm 插件将无法继续加载，构建时会抛出如下错误：

```text
The version of the SWC Wasm plugin you're using might not be compatible with 'builtin:swc-loader'.
```

如果你正在使用 SWC Wasm 插件，请重新构建插件，或升级到兼容 SWC 77 的版本。可以在 [plugins.swc.rs](https://plugins.swc.rs/) 中查找与当前 Rspack 版本匹配的插件版本。

> 详见：[常见问题 - SWC 插件版本不匹配](/errors/swc-plugin-version)。

### RSC 插件 \{#rsc-plugin-use-preinit}

此前，RSC 插件会包装客户端引用（Client Reference），并在渲染组件时插入 CSS `<link>` 标签。由于包装后的导出不再是原始的 Client Reference，某些导出形式可能无法保留 Client Reference 标识。

Rspack 2.2 不再包装客户端引用，而是通过 React 的 [`preinit`](https://react.dev/reference/react-dom/preinit) 加载客户端组件的 CSS。

这项调整改变了 RSC 中客户端组件 CSS 的加载方式，是一项针对 RSC 框架集成的破坏性变更。如果你正在集成 Rspack RSC 插件，请将 [`react-server-dom-rspack`](https://www.npmjs.com/package/react-server-dom-rspack) 同步升级到 `0.1.0`。

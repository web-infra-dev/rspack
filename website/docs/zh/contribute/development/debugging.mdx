# Debugging

## 通过 VS Code 调试

1. 安装 `go install github.com/go-delve/delve/cmd/dlv@latest`
2. 安装 VS Code 扩展 [rust-analyzer](https://marketplace.visualstudio.com/items?itemName=rust-lang.rust-analyzer) 和 [CodeLLDB](https://marketplace.visualstudio.com/items?itemName=vadimcn.vscode-lldb)
3. 通过执行 `pnpm install && pnpm -w build:cli:dev` 构建 `@rspack/cli` 和 napi binding
4. 在 VS Code 的 `Run and Debug` 栏中, 选择 `Debug Rspack` 开始调试 `@rspack/cli` 的启动过程。 该任务可以在 `.vscode/launch.json` 中配置，会同时启动 Node 和 Rust 的调试器。

:::note
其他工具集成的一般是 Rspack 的 release 版本，其中并不包含调试信息，这时候需要使用对应的含有debug 的版本进行override替换，方可调试。
:::

## 使用 `@rspack-debug/core`

集成 Rspack 的框架或工具通常依赖 release 版本的 `@rspack/core`。release 包适合正常构建，但不包含部分仅用于调试的能力。当你需要在本地排查问题时，可以在实际执行构建的项目中通过 package manager override 将 `@rspack/core` 替换为 `@rspack-debug/core`。

以 pnpm 为例：

```json title="package.json"
{
  "pnpm": {
    "overrides": {
      "@rspack/core": "npm:@rspack-debug/core@latest"
    },
    "peerDependencyRules": {
      "allowAny": ["@rspack/*"]
    }
  }
}
```

然后重新安装依赖，并继续运行原来的构建命令。例如项目通过 Rsbuild 构建时：

```bash
pnpm install
RSPACK_PROFILE=OVERVIEW RSPACK_TRACE_LAYER=perfetto rsbuild build
```

`@rspack-debug/core` 仅建议用于本地调试和问题诊断。如果正在排查特定版本的问题，建议将它固定到与原 `@rspack/core` 相同的版本；排查结束后应移除 override。

### 常见调试场景指南

#### 调试 Rust

只需在指定的 Rust 代码处设置断点后启动 `Debug Rspack` 即可进行调试。

#### 调试 JavaScript

启动 `Debug Rspack` 时，选择 `--inspect` 或 `--inspect-brk` 选项，然后启动 `Attach JavaScript` 并选择相应进程的 PID 即可。

#### 调试已启动的 Rspack 进程

当 Rspack 被集成到其他框架或工具（如 Nx）中时，可能难以独立使用 Launch 模式启动 Rspack。此时，可以通过 attach 模式调试代码。启动 `Attach Rust` 并选择 Rspack 所属进程的 PID 即可,启动 `Attach JavaScript` 即可调试 JavaScript。

#### 调试发生死锁的 Rspack 进程

当使用 `Attach Rust` 将调试器 attach 到 Rspack 所属进程后，点击 Debugger 的 Pause 按钮即可在死锁现场设置断点。

## 使用 allocative 分析内存 \{#memory-profiling-with-allocative}

debug（`build:binding:debug`，对应 Cargo 的 `release-debug` profile）和 profiling（`build:binding:profiling`）binding 内置 allocative。只有设置 `RSPACK_ALLOCATIVE_DIR` 后才会采集快照。

外部项目可以按照上文的覆盖依赖说明，使用包含此功能的 `@rspack-debug/core` 版本，或使用 profiling binding，无需自行编译 Rust。设置一个新的绝对路径输出目录，运行项目原有的构建命令，例如：

```bash
RSPACK_ALLOCATIVE_DIR=/tmp/rspack-memory-run-1 pnpm exec rsbuild build
```

打开 [Speedscope](https://www.speedscope.app/)，拖入 `/tmp/rspack-memory-run-1/0-build.allocative` 即可查看所有权树。取消设置 `RSPACK_ALLOCATIVE_DIR` 可停止采集快照。

本地构建 dev binding 时，需要显式启用 allocative。dev、CI 和 release 构建默认不包含此功能：

```bash
ALLOCATIVE=1 pnpm run build:binding:dev
pnpm run build:js
```

使用这个本地 binding 运行项目，并将 `RSPACK_ALLOCATIVE_DIR` 设置为新的绝对路径目录。每次构建或重新构建完成缓存收尾后，Rspack 会在 compiler 销毁前采集 compiler 和 compilation。每份快照包括字节权重（`.allocative`）、覆盖范围警告、元数据，以及按类型分组的模块和依赖条目数量。共享分配只统计一次，归入首次访问它的所有者下。

例如，在目标项目目录中运行：

```bash
RSPACK_ALLOCATIVE_DIR=/tmp/rspack-memory-run-1 \
  node /path/to/rspack/packages/rspack-cli/bin/rspack.js build
```

在 Rspack 仓库中整理快照和数量数据：

```bash
pnpm exec zx .agents/skills/rspack-allocative/scripts/render-profile.mjs \
  /tmp/rspack-memory-run-1/0-build.allocative \
  --out-dir /tmp/rspack-memory-run-1/report
```

报告包含 `.allocative` 快照副本、`counts.folded`、`counts.csv`、摘要，以及覆盖范围诊断。打开 [Speedscope](https://www.speedscope.app/)，拖入 `.allocative` 文件查看内存，或拖入 `counts.folded` 查看数量。使用 **Left Heavy** 视图搜索并放大所有权分支。folded 文件不携带单位：快照权重表示字节，数量权重表示当前模块图中的条目数。这些快照没有时间线，也不统计进程内全部对象的数量。字节权重包含已遍历对象拥有的堆分配和容器容量，但不包含无法访问的第三方内部状态、V8 内存，以及部分容器和分配器元数据。比较结果前请检查警告；总量既不是 RSS，也不是内存峰值。

恢复普通 dev、CI 或 release 构建时，取消设置 `ALLOCATIVE`。不要设置为 `ALLOCATIVE=0`，因为构建脚本会将非空的环境变量视为启用。debug 和 profiling binding 始终内置此功能，不受该构建变量影响；是否采集快照由 `RSPACK_ALLOCATIVE_DIR` 控制。

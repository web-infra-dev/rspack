# Debugging

## 通过 VS Code 调试

1. 安装 `go install github.com/go-delve/delve/cmd/dlv@latest`
2. 安装 VS Code 扩展 [rust-analyzer](https://marketplace.visualstudio.com/items?itemName=rust-lang.rust-analyzer) 和 [CodeLLDB](https://marketplace.visualstudio.com/items?itemName=vadimcn.vscode-lldb)
3. 通过执行 `pnpm install && pnpm -w build:cli:dev` 构建 `@rspack/cli` 和 napi binding
4. 在 VS Code 的 `Run and Debug` 栏中, 选择 `Debug Rspack` 开始调试 `@rspack/cli` 的启动过程。 该任务可以在 `.vscode/launch.json` 中配置，会同时启动 Node 和 Rust 的调试器。

:::note
其他工具集成的一般是 Rspack 的 release 版本，其中并不包含调试信息，这时候需要使用对应的含有debug 的版本进行override替换，方可调试。
:::

## 使用 `@rspack-debug/core`

集成 Rspack 的框架或工具通常依赖 release 版本的 `@rspack/core`。release 包适合正常构建，但不包含部分仅用于调试的能力。当你需要在本地排查问题时，可以在实际执行构建的项目中通过 package manager override 将 `@rspack/core` 替换为 `@rspack-debug/core`。

以 pnpm 为例：

```json title="package.json"
{
  "pnpm": {
    "overrides": {
      "@rspack/core": "npm:@rspack-debug/core@latest"
    },
    "peerDependencyRules": {
      "allowAny": ["@rspack/*"]
    }
  }
}
```

然后重新安装依赖，并继续运行原来的构建命令。例如项目通过 Rsbuild 构建时：

```bash
pnpm install
RSPACK_PROFILE=OVERVIEW RSPACK_TRACE_LAYER=perfetto rsbuild build
```

`@rspack-debug/core` 仅建议用于本地调试和问题诊断。如果正在排查特定版本的问题，建议将它固定到与原 `@rspack/core` 相同的版本；排查结束后应移除 override。

### 常见调试场景指南

#### 调试 Rust

只需在指定的 Rust 代码处设置断点后启动 `Debug Rspack` 即可进行调试。

#### 调试 JavaScript

启动 `Debug Rspack` 时，选择 `--inspect` 或 `--inspect-brk` 选项，然后启动 `Attach JavaScript` 并选择相应进程的 PID 即可。

#### 调试已启动的 Rspack 进程

当 Rspack 被集成到其他框架或工具（如 Nx）中时，可能难以独立使用 Launch 模式启动 Rspack。此时，可以通过 attach 模式调试代码。启动 `Attach Rust` 并选择 Rspack 所属进程的 PID 即可,启动 `Attach JavaScript` 即可调试 JavaScript。

#### 调试发生死锁的 Rspack 进程

当使用 `Attach Rust` 将调试器 attach 到 Rspack 所属进程后，点击 Debugger 的 Pause 按钮即可在死锁现场设置断点。

## rust-lldb

`rust-lldb` 可用于从 debug 版本中获取 panic 信息

```bash
rust-lldb -- node /path/to/rspack build
```

启动后，按住 `r` 来执行程序。

例如，`examples/arco-pro` 运行崩溃了并且没有任何信息在[这个修复](https://github.com/web-infra-dev/rspack/pull/3195/files) 之前:

## Allocative 内存快照 \{#allocative-memory-snapshots}

启用 allocative 插桩，构建本地 binding 和 JavaScript 包：

```bash
ALLOCATIVE=1 pnpm run build:binding:dev
pnpm run build:js
```

为每次运行指定新的输出目录，并暴露 Node.js GC：

```bash
RSPACK_ALLOCATIVE_DIR=/tmp/rspack-memory \
  node --expose-gc packages/rspack-cli/bin/rspack.js build
```

在 build 或 rebuild 的缓存收尾完成后，Rust 会等待一个全局 JavaScript 回调。回调先执行 `gc()`，再写入 V8 堆快照，随后 Rust 才遍历 compiler。每次采集会生成配套的 `.heapsnapshot`、`.allocative` 和 `.objects.json` 文件。未注册回调的独立 Rust 程序仍只生成 Rust profile。一个进程只允许一个 V8 环境注册回调。

启用 allocative 时，native class 实例包含不可枚举、只读的字符串属性 `__rspackRustPtr` 和 `__rspackRustType`。指针标识 Rust binding wrapper 在 N-API 中的最终地址，与 wrapper 引用的 module 或 resolver 地址不同。弱引用注册表记录存活的 wrapper，不阻止回收，也不遍历可能正在工作的 native target。compiler 遍历独立测量 native 内存；binding 身份记录不增加字节权重。

将配套快照转换为现有 allocative 火焰图工具支持的 folded stacks：

```bash
node scripts/v8-to-allocative.mjs /tmp/rspack-memory/0-build.heapsnapshot
```

脚本生成 `.js.allocative`、`.combined.allocative` 和 `.links.json` 文件。关联报告将 V8 节点 ID 匹配到 Rust wrapper 的地址、类型和路径。JavaScript 字节权重对每个 V8 节点的浅层 `self_size` 只计数一次，通过广度优先遍历归属到首个强引用 owner。共享引用和循环不会重复计数，弱引用不构成所有权。这种归属方式不是支配树，也不代表 retained size。路径默认最多 32 层，可通过 `--max-depth` 调整；无法从根节点经强引用到达的对象单独分组。结果不代表 RSS 或峰值内存，地址仅在同一进程的采集中有意义。
